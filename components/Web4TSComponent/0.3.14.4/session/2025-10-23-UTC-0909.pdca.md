## **📋 PLAN**

### **The Crisis**

**User Report:** "just started a fresh shell... seeeeems dead"

Tab completion hangs. No response from `web4tscomponent` command.

### **Root Cause Discovery**

**Investigation revealed INFINITE LOOP:**
```bash
# scripts/web4tscomponent (production CLI)
exec "$PROJECT_ROOT/scripts/web4tscomponent" test shell "0.3.14.4" "$@"
# ↑ CALLS ITSELF! ↑
```

**Why?**
1. `initProject` calls `generateVersionWrappers`
2. `generateVersionWrappers` creates wrappers for ALL versions including 0.3.14.4
3. Wrapper for 0.3.14.4 is placed in `scripts/versions/web4tscomponent-v0.3.14.4`
4. BUT it ALSO overwrote `components/Web4TSComponent/0.3.14.4/web4tscomponent`!
5. `scripts/web4tscomponent` → `latest/web4tscomponent` → wrapper → calls `scripts/web4tscomponent` → LOOP!

### **Three Critical Bugs**

**Bug 1: Current Version Wrapped**
- `generateVersionWrappers` shouldn't create wrapper for the CURRENT running version
- Current version is THE production CLI - it should be the REAL launcher, not a wrapper!

**Bug 2: Symlink Resolution**
- `web4tscomponent` uses `$(dirname "$0")` which doesn't resolve through symlinks
- `scripts/web4tscomponent` → `latest/web4tscomponent` (double symlink) breaks path resolution

**Bug 3: Old Code Test Access**
- Old versions do `path.join(process.cwd(), 'test')` to find tests
- When in test/data, they look for `test/data/test/`
- Tests were copied to `test/data/components/{Component}/{Version}/test/`
- Can't modify old code (frozen!) so must adapt environment

### **Architectural Insights**

**The "Wrapper Paradox":**
- Wrappers delegate to latest version for isolation
- But latest version MUST be the real CLI, not a wrapper
- Solution: `generateVersionWrappers` skips `context.version`

**The "Frozen Code" Challenge:**
- Old versions' code can't be modified
- Their assumptions about paths must be honored
- Solution: Adapt environment to match old code's expectations

**The "Triple Symlink" Resolution:**
- `scripts/` → `components/.../latest/` → `version/file`
- `$(dirname "$0")` only resolves one level
- Solution: `readlink -f` / `realpath` resolves full chain
