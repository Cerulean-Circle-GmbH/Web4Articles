## **🎯 PLAN**

### Context: The Chicken-and-Egg Problem

**Current Situation:**
- `test/data` should be a "virtual project root" with its own `source.env`
- `web4tscomponent test shell` should start bash in `test/data` with isolated completion environment
- But `testShell()` method is in test version (0.3.14.4), while `latest` symlink points to prod (0.3.13.2)
- User can't call the test version because `web4tscomponent` command resolves via `latest` → prod

**The Problem:**
```
User wants: web4tscomponent test shell
Reality: latest → 0.3.13.2 (prod, doesn't have testShell method)
Need: test → 0.3.14.4 (test version, has testShell method)

But test/data needs:
- scripts/web4tscomponent (symlink to test version)
- source.env (with proper WEB4_PROJECT_ROOT pointing to test/data)
- Isolated completion environment that doesn't affect main project
```

### Research: Component Spec - Test Isolation

**Key Insight:** ProjectRootMocker is for TypeScript tests (vitest), not for bash completion testing.

### Design: Proper Bootstrapping Order

**Objective:** Make `test/data` a fully functional isolated project root for completion testing.

#### Phase 1: Prerequisites (Already Done)
1. ✅ `test/data/source.env` exists (created by initProject)
2. ✅ `test/data/package.json` exists
3. ✅ `test/data/tsconfig.json` exists
4. ✅ `test/data/node_modules` symlink exists

#### Phase 2: Bootstrap Sequence (Needs Design)

**Step 1: Create scripts/versions/ structure in test/data**

```
test/data/
  ├── scripts/
  │   ├── web4tscomponent → ../../web4tscomponent (symlink to test version)
  │   └── versions/
  │       └── web4tscomponent/
  │           └── 0.3.14.4 → ../../../web4tscomponent (symlink)
  └── source.env (WEB4_PROJECT_ROOT points to test/data)
```

**Why?**
- `_web4_auto_register_completions` scans `$WEB4_PROJECT_ROOT/scripts/versions` for CLIs
- Without `scripts/versions/`, completion registration fails
- `test/data` must look like a real project root to bash

**Step 2: Adjust source.env for test/data context**

Current `source.env.template` line ~5:
```bash
export WEB4_PROJECT_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
```

**Problem:** In test/data context, this points to `<component>/0.3.14.4/test/data` ✅
**Good:** This is actually correct! `test/data` SHOULD be the project root in test context.

**Step 3: Ensure CLI executable is callable**

From `test/data`, user types `web4tscomponent <TAB>`.

Bash completion needs:
1. `web4tscomponent` command available in PATH → via `scripts/web4tscomponent` symlink
2. `_web4_auto_register_completions` finds it → via `scripts/versions/web4tscomponent/0.3.14.4`

**Current Gap:** `scripts/` doesn't exist in test/data!

#### Phase 3: initProject Enhancements Needed

**Proposal:** Extend `initProject(targetDir)` to detect test isolation mode:

```typescript
async initProject(targetDir?: string): Promise<this> {
  const projectRoot = targetDir || process.cwd();
  
  // Detect if we're initializing test/data (test isolation mode)
  const isTestIsolation = projectRoot.includes('/test/data');
  
  if (isTestIsolation) {
    // MODE: Test Isolation
    // 1. Create source.env (already done)
    // 2. Create scripts/versions/ structure (NEW)
    // 3. Symlink to test version CLI (NEW)
    // 4. Configure WEB4_PROJECT_ROOT correctly (already correct)
    await this.initTestIsolationEnvironment(projectRoot);
  } else {
    // MODE: Normal Project
    // 1. Create source.env
    // 2. Create package.json
    // 3. Create tsconfig.json
    // 4. Create global node_modules
    await this.initNormalProject(projectRoot);
  }
}
```

#### Phase 4: Access Pattern

**Current Problem:** `web4tscomponent test shell` calls prod version (0.3.13.2) via `latest` symlink.

**Solution Options:**

**Option A: Direct Version Call (Immediate)**
```bash
./components/Web4TSComponent/test/web4tscomponent test shell
```
- ✅ Works immediately (no changes needed)
- ✅ Explicit about which version is being tested
- ❌ Verbose path

**Option B: Environment Variable Override**
```bash
export WEB4_TEST_MODE=1
web4tscomponent test shell
```
- ✅ Clean command
- ❌ Requires CLI to check env var and delegate to test version
- ❌ More complex

**Option C: Dedicated Test Command in Prod**
```bash
web4tscomponent testInDev shell
```
- ✅ Works from any version
- ❌ Ugly command name
- ❌ Requires prod version to know about test version

**Recommendation:** Option A (direct version call) for now.

### Design: Test Isolation Architecture

```
Project Root (Main)
├── components/Web4TSComponent/
│   ├── 0.3.13.2/ (prod - via latest symlink)
│   ├── 0.3.14.4/ (test - new scenario completion)
│   │   ├── web4tscomponent (CLI executable)
│   │   ├── test/
│   │   │   ├── data/ (VIRTUAL PROJECT ROOT for testing)
│   │   │   │   ├── scripts/
│   │   │   │   │   ├── web4tscomponent → ../../web4tscomponent
│   │   │   │   │   └── versions/
│   │   │   │   │       └── web4tscomponent/
│   │   │   │   │           └── 0.3.14.4 → ../../../web4tscomponent
│   │   │   │   ├── source.env (WEB4_PROJECT_ROOT=/path/to/test/data)
│   │   │   │   ├── package.json
│   │   │   │   ├── tsconfig.json
│   │   │   │   └── node_modules → ../../../../node_modules
│   │   │   └── sh/ (test scripts)
│   │   └── src/
│   ├── latest → 0.3.13.2
│   ├── test → 0.3.14.4
│   └── prod → 0.3.13.2
└── scripts/
    ├── web4tscomponent → ../components/Web4TSComponent/latest/web4tscomponent
    └── versions/
        └── web4tscomponent/
            └── 0.3.13.2 → ../../Web4TSComponent/latest/web4tscomponent
```

**Key Principles:**

1. **test/data is a REAL project root** - has all structures a project needs
2. **Isolation via WEB4_PROJECT_ROOT** - source.env sets it to test/data
3. **CLI access via scripts/** - test/data/scripts/ mirrors main project structure
4. **Version-specific testing** - test/data uses test version, not latest
5. **No contamination** - test/data changes don't affect main project

### Design: test() Method Delegation

**Current Code (lines 1779-1787):**
```typescript
async test(scope: string = 'all', ...references: string[]): Promise<this> {
  // Detect mode: selective testing vs full suite
  const selectiveScopes = ['file', 'describe', 'itCase'];
  const isSelectiveMode = selectiveScopes.includes(scope);
  
  if (isSelectiveMode) {
    // MODE 2: Selective testing
    return await this.testSelective(scope, references);
  }
```

**Needed Enhancement:**
```typescript
async test(scope: string = 'all', ...references: string[]): Promise<this> {
  // MODE 1: Test shell (bash completion testing)
  if (scope === 'shell') {
    return await this.testShell();
  }
  
  // MODE 2: Selective testing
  const selectiveScopes = ['file', 'describe', 'itCase'];
  if (selectiveScopes.includes(scope)) {
    return await this.testSelective(scope, references);
  }
  
  // MODE 3: Full test suite
  // ... existing code
}
```

**Also Change:** `testShell()` visibility from `private` → `protected`
