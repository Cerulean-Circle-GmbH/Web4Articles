### **1. createPDCA - Cross-Component PDCA Creation**

**Purpose:** Programmatically create new PDCAs with auto-populated metadata and bidirectional chaining

**Syntax:**
```bash
pdca createPDCA "<title>" "<objective>" [sessionDirectory] [dryRun]
```

**Parameters:**
- `title` (required): Short descriptive title for the PDCA
- `objective` (required): Clear objective statement
- `sessionDirectory` (optional): Absolute path to target session directory (enables cross-component creation)
- `dryRun` (optional): Set to `true` to preview without creating file

**Examples:**
```bash
# Example 1: Create in default PDCA component session
pdca createPDCA "Fix Bug" "Resolve test failure in component X"

# Example 2: Create in ANY component directory (cross-component feature)
pdca createPDCA "Demo" "Show PDCA commands" \
  /Users/Shared/Workspaces/2cuGitHub/Web4Articles/components/Web4TSComponent/0.3.17.1/session

# Example 3: Dry run to preview
pdca createPDCA "Title" "Objective" ./custom/session true
```

**What It Does:**
- ✅ Reads official template from `scrum.pmo/roles/_shared/PDCA/template.md`
- ✅ Generates UTC timestamp filename: `YYYY-MM-DD-UTC-HHMM.pdca.md`
- ✅ Auto-populates ALL metadata placeholders (CMM_STATUS, AGENT_NAME, BRANCH, UTC_TIMESTAMP, etc.)
- ✅ Establishes bidirectional chain: Updates previous PDCA's "Next PDCA:" link automatically
- ✅ Creates session directory if it doesn't exist
- ✅ **AI Content Population Mandate**: AI immediately populates all content sections based on objective

**Use Cases:**
- Starting new feature/task documentation from scratch
- Creating PDCAs in any component (not just PDCA component)
- Ensuring consistent PDCA structure across all sessions
- Boss presentations (this PDCA was created with this command!)

**Source PDCA:** [0726 (cross-component)](../../../PDCA/0.3.6.1/session/2025-11-04-UTC-0726.pdca.md), [0957 (AI mandate)](../../../PDCA/0.3.6.1/session/2025-11-04-UTC-0957.pdca.md)

### **2. rename - File Renaming with 4 Strategies + Atomic Git Commits**

**Purpose:** Rename PDCA files using different strategies with automatic git commit/push and bidirectional link updates

**Syntax:**
```bash
pdca rename <file> <case> [dryRun]
```

**Parameters:**
- `file` (required): Path to PDCA file to rename
- `case` (required): Rename strategy - `now` | `creationDate` | `strip` | `feature`
- `dryRun` (optional): Set to `true` to preview without renaming

#### **Case 1: `now` - Update to Current UTC Timestamp**

**Example:**
```bash
pdca rename 2025-10-28-UTC-1632.pdca.md now
# Result: 2025-11-04-UTC-1121.pdca.md (current UTC time)
```

**Use Case:** Update stale PDCA timestamp to reflect current work time

#### **Case 2: `creationDate` - Restore Git Creation Timestamp**

**Example:**
```bash
pdca rename 2025-11-04-UTC-1121.pdca.md creationDate
# Result: 2025-11-04-UTC-1011.pdca.md (original git creation date from git log)
```

**Use Case:** Fix manually renamed file to match its original git creation timestamp for chronological accuracy

#### **Case 3: `strip` - Remove Descriptive Text**

**Example:**
```bash
pdca rename 2025-10-28-UTC-1632.test-hang-investigation.pdca.md strip
# Result: 2025-10-28-UTC-1632.pdca.md
```

**Use Case:** Clean filename for archival, final version, or removing temp descriptive text

#### **Case 4: `feature` - Add .feature. Marker**

**Example:**
```bash
pdca rename 2025-11-04-UTC-1011.pdca.md feature
# Result: 2025-11-04-UTC-1011.feature.pdca.md
```

**Use Case:** Mark PDCA as feature development (vs bug fix, refactor, etc.) for categorization

**What It Does:**
- ✅ Performs `git mv` with fallback to `fs.rename`
- ✅ Updates all bidirectional links in other PDCAs automatically
- ✅ **CRITICAL FIX (PDCA 0829)**: Atomic commit and push ALWAYS (even if no links to update)
- ✅ Creates target directories if needed
- ✅ Dry run mode to preview changes without applying

**Source PDCA:** [0829 (atomic commit bug fix)](../../../PDCA/0.3.6.1/session/2025-11-04-UTC-0829.pdca.md)

### **4. cmm3check - CMM3 Compliance Validation**

**Purpose:** Validate PDCA files against CMM3 requirements with auto-fix capability

**Syntax:**
```bash
pdca cmm3check <file> [dryRun]
```

**Parameters:**
- `file` (required): Path to PDCA file to validate
- `dryRun` (optional): Set to `true` to preview fixes without applying

**Examples:**
```bash
# Check compliance (reports violations)
pdca cmm3check components/Web4TSComponent/0.3.17.1/session/2025-11-04-UTC-1121.pdca.md

# Auto-fix mode (fixes some violations automatically)
pdca cmm3check <file> false
```

**What It Checks (11+ Violation Types):**
- **1a-1j**: Required sections (SUMMARY, PLAN, DO, CHECK, ACT, EMOTIONAL REFLECTION, PDCA PROCESS UPDATE, etc.)
- **1k**: Unpopulated `{{}}` placeholders (metadata must be filled)
- **1l**: Missing DoR/DoD sections (mandatory as of 2025-11-04, PDCA 0829)
- **3a-3c**: Dual link format validation (GitHub URL | § notation)
- **4a-4d**: Timestamp format validation (YYYY-MM-DD-UTC-HHMM)
- **5a/5c, 6a, 7a/7b**: Additional compliance checks (header format, section structure, etc.)

**What It Does:**
- ✅ Reports all violations with descriptive error messages
- ✅ Auto-fix available for some violations (dual link format, etc.)
- ✅ Returns exit code 0 if compliant, non-zero if violations found
- ✅ Dry run mode to preview fixes without applying
- ✅ Used in CI/CD pipelines for quality gates

**Source PDCA:** [0829 (DoR/DoD enforcement - violation 1l)](../../../PDCA/0.3.6.1/session/2025-11-04-UTC-0829.pdca.md)

### **5. rewritePDCA - Fix Corrupted PDCAs with Smart Content Preservation**

**Purpose:** Replace corrupted PDCAs with fresh template while preserving timestamp, title, objective, and valid content sections

**Syntax:**
```bash
pdca rewritePDCA <file> [dryRun]
```

**Parameters:**
- `file` (required): Path to corrupted PDCA file
- `dryRun` (optional): Set to `true` to preview without rewriting

**Examples:**
```bash
# Rewrite corrupted PDCA
pdca rewritePDCA components/PDCA/0.3.6.1/session/2025-11-03-UTC-1400.pdca.md

# Dry run to preview
pdca rewritePDCA <file> true
```

**What It Does:**
- ✅ **Preserves timestamp**: Filename stays the same (true in-place rewrite, PDCA 1507)
- ✅ **Auto-extracts title**: From line 1 (`# 📋 **PDCA Cycle: TITLE - ...**`)
- ✅ **Auto-extracts objective**: From header (`**🎯 Objective:** ...`)
- ✅ **Auto-populates ALL metadata**: Uses shared `populateBoilerplateInternal()` helper (PDCA 0923)
- ✅ **Smart Content Preservation (Option B)**: Salvages valid content sections (SUMMARY, PLAN, DO, CHECK, ACT, etc.) and inserts into fresh template (PDCA 1020/1025/1104)
- ✅ **Line-by-line parsing**: Robust section merging prevents template bleeding (PDCA 1104 bug fix)
- ✅ Reads fresh template from `scrum.pmo/roles/_shared/PDCA/template.md`
- ✅ Writes to SAME filename (not create-new-delete-old)

**Smart Content Preservation Logic:**
1. Extract all `## **SectionName**` sections from corrupted PDCA
2. Validate each section: length > 50 chars, < 10% placeholders, no corruption markers
3. Load fresh template
4. Merge: Insert valid extracted content into template, reset invalid sections to template
5. Result: Clean structure + preserved valid content

**Use Cases:**
- PDCA is corrupted (missing sections, invalid structure, broken by manual editing)
- PDCA fails cmm3check validation
- PDCA has unpopulated metadata placeholders
- Restore PDCA after accidental damage

**Source PDCAs:**
- [0923 (auto-population)](../../../PDCA/0.3.6.1/session/2025-11-04-UTC-0923.pdca.md)
