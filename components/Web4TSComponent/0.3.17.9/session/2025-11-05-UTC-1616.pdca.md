## 1. Problem Statement

**Observable Behavior:**
- `web4tscomponent test file` (execution) - ✅ Shows all 41 test files correctly
- `web4tscomponent test file <Tab>` (completion) - ❌ Shows only `1:` instead of all 41 file numbers
- `web4tscomponent test file 2<Tab>` (completion) - ❌ Shows "(no completions available)" instead of describe blocks
- `web4tscomponent test itCase <Tab>` (completion, second press) - ❌ Falls back to bash file completion (`.test.ts` files) instead of hierarchical output

**Expected Behavior (from 0.3.17.4):**
- `web4tscomponent test file <Tab>` should show all file numbers: `1: 2: 3: ... 41:`
- `web4tscomponent test file 2<Tab>` should show describe blocks for file 2
- `web4tscomponent test itCase <Tab>` should consistently show hierarchical output on every Tab press

**Root Cause Hypothesis:**
The completion callback `referencesParameterCompletion()` is being invoked correctly and returns data, but the bash completion script is not extracting WORDS correctly from the hierarchical display format, or the completion routing is failing on subsequent Tab presses.

**Impact:**
- User experience regression: Tab completion does not provide expected suggestions
- Forces users to memorize file/describe/itCase numbers instead of using Tab to discover them
- Inconsistent with 0.3.17.4 behavior

## 2. Root Cause Analysis (5 Whys)

**Why 1:** Why does `test file <Tab>` show only `1:` instead of all numbers?  
→ The bash completion script is extracting only one WORD from the completion output.

**Why 2:** Why is bash extracting only one WORD?  
→ Either `getAllFilesHierarchical()` returns display in a format that bash can't parse, or `formatCompletionOutput()` is not generating WORD lines correctly.

**Why 3:** Why might `formatCompletionOutput()` not generate WORD lines correctly?  
→ `getAllFilesHierarchical()` returns `display` as a single-element array with all files joined by newlines (`lines.join('\n')`), but `formatCompletionOutput()` may not be splitting this properly.

**Why 4:** Why does the hierarchical format work for execution but not completion?  
→ Execution calls `testItCase()` which displays the output directly. Completion calls `referencesParameterCompletion()` which returns values that must be processed by `formatCompletionOutput()`.

**Why 5:** Why did this work in 0.3.17.4 but not after the self-discovery architecture refactoring?  
→ The refactoring in session 2025-11-05-UTC-1223 changed command routing but did not modify completion logic. However, the completion may be affected by changes in how `this.context` or `this.component` are used for callback resolution.

**Root Cause:**
`formatCompletionOutput()` expects `values: string[]` where each element is a display line. However, `getAllFilesHierarchical()` returns `display` as `[lines.join('\n')]` (single element with embedded newlines). When `formatCompletionOutput()` processes this in the "Multi-line format" branch (lines 2180-2228), it iterates over the array elements, not the individual lines within the single element. This causes it to extract only the first token from the entire joined string.

### Current Implementation

**`getAllFilesHierarchical()` (TestFileParser.ts:288-313):**
```typescript

  display: string[];
  tokens: string[];
} {
  const files = TestFileParser.scanTestFiles(testDir);
  const display: string[] = [];
  const tokens: string[] = [];

  display.push(lines.join('\n'));  // ❌ Single element array!

```

**`formatCompletionOutput()` (DefaultCLI.ts:2095-2292):**
```typescript

  if (values.length > 0) {
    // Multi-line format: numbered list like "1: methodName <params>"

```

**The Bug:**
- `getAllFilesHierarchical()` returns `display: ['1:\tfile1.ts\n2:\tfile2.ts\n...']` (single element)
- `formatCompletionOutput()` calls `values.forEach((value: string) => ...)` which iterates once
- `value.split("\n")[0]` extracts only `"1:\tfile1.ts"` (first line)
- Regex extracts token `"1"` from first line only
- Result: Only `WORD: 1` is generated, not `WORD: 1`, `WORD: 2`, ..., `WORD: 41`

## 5. Solution Design

### Option A: Fix `formatCompletionOutput()` to split embedded newlines

**Change:** Modify `formatCompletionOutput()` to split single-element arrays with embedded newlines into individual lines before extracting WORDS.

**Pros:**
- Keeps `getAllFilesHierarchical()` unchanged
- Centralizes fix in one place (`formatCompletionOutput()`)
- No impact on other parts of the system

**Cons:**
- `formatCompletionOutput()` becomes more complex
- Mixes two different formats (array of lines vs single string with newlines)

### Option B: Fix `getAllFilesHierarchical()` to return individual lines

**Change:** Modify `getAllFilesHierarchical()` to return `display` as an array of individual lines, not a single joined string.

**Pros:**
- Simpler, more consistent format
- `formatCompletionOutput()` already handles array of lines correctly
- Aligns with the expected contract: `string[]` should be an array of strings, not an array containing one big string

**Cons:**
- Requires changing `getAllFilesHierarchical()` and potentially other hierarchical methods
- May impact how the display is shown (single vs multiple console.log calls)

### Option C: Return tokens directly for simple completions

**Change:** For file/describe/itCase references, return `tokens` directly instead of going through hierarchical display format.

**Pros:**
- Simplest solution for numeric tokens
- No formatting complexity

**Cons:**
- Loses the hierarchical display UX (file names, describe names, etc.)
- Regression in user experience

```typescript
// Before extracting WORDs, split values that contain newlines into individual lines
const expandedValues: string[] = [];
values.forEach((value: string) => {
  if (value.includes("\n")) {
    // Split multi-line values into individual lines
    expandedValues.push(...value.split("\n").filter(line => line.trim()));
  } else {
    expandedValues.push(value);
  }
});

expandedValues.forEach((value: string) => {
  // ... extract WORD from each line ...
});
```

**How it works:**
1. When `values = ['1:\tfile1\n2:\tfile2\n...']` (single element with newlines) is received
2. `expandedValues` becomes `['1:\tfile1', '2:\tfile2', ...]` (multiple elements)
3. Each line is processed to extract one WORD token
4. Result: `WORD: 1`, `WORD: 2`, ..., `WORD: 41` are all generated
