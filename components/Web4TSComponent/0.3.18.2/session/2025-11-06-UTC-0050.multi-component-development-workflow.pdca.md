## Problem Statement

**Context**: When developing Web4 components, there are TWO codebases in play:
1. **Web4TSComponent** (Infrastructure / Producer / Templates)
2. **Target Component** (e.g., IdealMinimalComponent / Consumer / Generated)

**Challenge**: It's easy to get CONFUSED about:
- Where to fix bugs (infrastructure vs target)?
- What to build and in what order?
- How to apply template changes to existing components?
- When changes propagate automatically vs manually?

**Consequence**: Wasted time building the wrong thing, or forgetting critical build steps.

**Goal**: Document a clear decision tree and workflow for multi-component development.

**Example Location**: `components/IdealMinimalComponent/0.3.18.0/`

- **Shell Scripts**: `src/sh/*.sh` (copied from templates)

- Domain-specific methods (e.g., `process`, `analyze`, `report`)
- Delegation to Web4TSComponent for infrastructure
- Own business logic

**Build Command**: `idealminimalcomponent build` or `./src/sh/build.sh`

**Test Command**: `idealminimalcomponent test file <N>` (if it has tests)

### Part 2: Decision Tree - Where to Fix?

#### Question 1: Is it a CLI Framework Issue?

**Examples**:
- Tab completion not working
- Method discovery broken
- Command execution failing
- `on` context not loading
- Signature parsing errors

**Fix Location**: ✅ **Web4TSComponent** - `src/ts/layer2/DefaultCLI.ts`

**Why**: All generated CLIs inherit from `DefaultCLI`, so the fix propagates automatically.

**Build Required**: 
1. ✅ Build Web4TSComponent
2. ❌ No need to rebuild target components (they use the built `dist/` files)

**Test Strategy**:
```bash
# 1. Fix DefaultCLI.ts in Web4TSComponent
# 2. Build Web4TSComponent
web4tscomponent build

# 3. Test with Web4TSComponent's own CLI
web4tscomponent links

# 4. Test with a target component CLI
idealminimalcomponent links

# 5. If both work, fix is good!
```

---

#### Question 2: Is it a Template Issue?

**Examples**:
- Missing methods in generated components
- Wrong import paths in templates
- Missing method discovery in `DefaultComponent.ts.template`
- Missing interfaces in generated components

**Fix Location**: ✅ **Web4TSComponent** - `templates/ts/*.ts.template` or `templates/sh/*.sh.template`

**Why**: Templates are the SOURCE for generated components.

**Build Required**:
1. ✅ Build Web4TSComponent (to compile template loading logic if TypeScript)
2. ❌ NO automatic propagation to existing components!

**Propagation Strategy**:

**Option A: Remove & Recreate (RECOMMENDED for breaking changes)**
```bash
# 1. Fix template in Web4TSComponent
# 2. Build Web4TSComponent
web4tscomponent build

# 3. Remove old version
web4tscomponent removeVersion IdealMinimalComponent 0.3.18.0

# 4. Create new version from fixed template
web4tscomponent create IdealMinimalComponent 0.3.18.0

# 5. Test
idealminimalcomponent links
```

**Option B: Manual Update (for small fixes)**
```bash
# 1. Fix template in Web4TSComponent
# 2. Manually apply the same fix to target component
# 3. Build target component
idealminimalcomponent build
```

**Option C: updateBuildSystem (for shell scripts only)**
```bash
# 1. Fix shell script template in Web4TSComponent
# 2. Run updateBuildSystem on target
web4tscomponent on IdealMinimalComponent 0.3.18.0 updateBuildSystem

# ⚠️ Only updates scripts, NOT TypeScript files!
```

---

#### Question 3: Is it an Infrastructure Method?

**Examples**:
- `test` command broken
- `build` command issues
- `clean` command problems
- `tree` visualization wrong
- `links` display incorrect

**Fix Location**: ✅ **Web4TSComponent** - `src/ts/layer2/DefaultWeb4TSComponent.ts`

**Why**: Target components DELEGATE these methods to Web4TSComponent.

**Build Required**:
1. ✅ Build Web4TSComponent
2. ❌ No need to rebuild target components (delegation is dynamic)

**Test Strategy**:
```bash
# 1. Fix DefaultWeb4TSComponent.ts
# 2. Build Web4TSComponent
web4tscomponent build

# 3. Test with Web4TSComponent
web4tscomponent test file 13

# 4. Test with target component (via delegation)
idealminimalcomponent test file 1

# 5. Both should work!
```

---

#### Question 4: Is it a Shell Script Issue?

**Examples**:
- `build.sh` broken
- `clean-global.sh` deleting wrong files
- `lib-project-root.sh` path resolution wrong

**Fix Location**: 
- ✅ **Web4TSComponent** - `src/sh/*.sh` (source)
- ✅ **Web4TSComponent** - `templates/sh/*.sh.template` (template)
- ⚠️ **Target Component** - `src/sh/*.sh` (if already created)

**Why**: Shell scripts exist in BOTH places and need to be kept in sync!

**Build Required**:
1. ❌ No TypeScript build needed (shell scripts are not compiled)
2. ✅ BUT must update template AND apply to existing components

**Propagation Strategy**:
```bash
# 1. Fix shell script in Web4TSComponent/src/sh/
# 2. Update the template Web4TSComponent/templates/sh/
# 3. Apply to existing target components:

# Option A: updateBuildSystem (shell only)
web4tscomponent on IdealMinimalComponent 0.3.18.0 updateBuildSystem

# Option B: Remove & Recreate
web4tscomponent removeVersion IdealMinimalComponent 0.3.18.0
web4tscomponent create IdealMinimalComponent 0.3.18.0

# Option C: Manual copy (quick test)
cp components/Web4TSComponent/0.3.18.2/src/sh/clean-global.sh \
   components/IdealMinimalComponent/0.3.18.0/src/sh/clean-global.sh
```

---

#### Question 5: Is it a Domain-Specific Issue?

**Examples**:
- Target component's own methods broken
- Business logic errors
- Domain-specific data processing

**Fix Location**: ✅ **Target Component** - `src/ts/layer2/Default<ComponentName>.ts`

**Why**: This is the target component's OWN code, not infrastructure.

**Build Required**:
1. ❌ No need to build Web4TSComponent
2. ✅ Build target component only

**Test Strategy**:
```bash
# 1. Fix the target component's TypeScript
# 2. Build target component
idealminimalcomponent build

# 3. Test target component
idealminimalcomponent <your-domain-method>
```

### Part 3: Build Order Matrix

| What Changed | Build Order | Notes |
|--------------|-------------|-------|
| `DefaultCLI.ts` | 1. Web4TSComponent<br>2. DONE | CLI inheritance auto-applies |
| `DefaultWeb4TSComponent.ts` | 1. Web4TSComponent<br>2. DONE | Delegation auto-applies |
| `*.ts.template` | 1. Web4TSComponent<br>2. Remove/Create Target | Templates don't auto-apply |
| `*.sh.template` | 1. Update template<br>2. `updateBuildSystem` OR Remove/Create | Shell scripts need explicit sync |
| `Web4TSComponent/src/sh/*.sh` | 1. Update source<br>2. Update template<br>3. Apply to targets | Shell in both places |
| Target component logic | 1. Target Component<br>2. DONE | No Web4TSComponent build needed |

### Part 4: The Confusion Matrix - What Builds What?

#### Scenario A: "I fixed DefaultCLI.ts and built Web4TSComponent, but idealminimalcomponent still broken!"

**Diagnosis**: ❌ **WRONG EXPECTATION**

**Reality**: If the target component's CLI is still failing, the issue is probably in:
1. The target component's OWN TypeScript (need to rebuild target)
2. OR the template (need to remove/create target)

**Fix**:
```bash
# Check if target component was created BEFORE the template fix
# If yes, remove and recreate
web4tscomponent removeVersion IdealMinimalComponent 0.3.18.0
web4tscomponent create IdealMinimalComponent 0.3.18.0
```

---

#### Scenario B: "I fixed the template but nothing changed!"

**Diagnosis**: ✅ **CORRECT - Templates don't auto-apply**

**Reality**: Templates are only used during `create`. Existing components are NOT updated.

**Fix**:
```bash
# Remove and recreate to apply template changes
web4tscomponent removeVersion IdealMinimalComponent 0.3.18.0
web4tscomponent create IdealMinimalComponent 0.3.18.0
```

---

#### Scenario C: "I built Web4TSComponent, why do I need to build it again?"

**Diagnosis**: ⚠️ **MAYBE WRONG**

**Reality**: You DON'T need to rebuild unless:
1. You made more changes to TypeScript
2. The first build failed
3. You're unsure if changes were applied

**Check**:
```bash
# Check if dist/ files are newer than src/ files
ls -lt components/Web4TSComponent/0.3.18.2/dist/ts/layer2/DefaultCLI.js
ls -lt components/Web4TSComponent/0.3.18.2/src/ts/layer2/DefaultCLI.ts

# If dist is newer, no rebuild needed!
```

---

#### Scenario D: "Do I test in Web4TSComponent or target component?"

**Diagnosis**: ✅ **BOTH!**

**Reality**: Test in BOTH to ensure:
1. Web4TSComponent's own methods work
2. Delegation from target components works

**Test Strategy**:
```bash
# 1. Test Web4TSComponent's own CLI
web4tscomponent links
web4tscomponent test file 13

# 2. Test target component CLI (delegation)
idealminimalcomponent links
idealminimalcomponent test file 1

# 3. Test target component with "on" (explicit context)
web4tscomponent on IdealMinimalComponent 0.3.17.8 links
```

### Part 6: The Golden Rules

#### Rule 1: Fix Close to the Root

**Principle**: Fix in the most GENERIC place possible.

```
DefaultCLI.ts (most generic)
  ↓ inherited by
Web4TSComponentCLI.ts (Web4TSComponent's CLI)
  ↓ AND
IdealMinimalComponentCLI.ts (target's CLI)
```

**If the bug affects BOTH** → Fix in `DefaultCLI.ts`

**If the bug affects only Web4TSComponent** → Fix in `Web4TSComponentCLI.ts`

**If the bug affects only target** → Fix in target's CLI

---

#### Rule 2: Templates Are NOT Live Code

**Critical Understanding**:
- Templates are BLUEPRINTS
- They are used ONCE during `create`
- Fixing a template does NOT fix existing components
- You MUST remove/recreate OR manually update

**Example**:
```bash
# ❌ WRONG - thinking template fixes auto-apply
# Fix template
# Build Web4TSComponent
# Expect existing component to work
# → NOPE! Still broken!

# ✅ RIGHT - understanding templates are blueprints
# Fix template
# Build Web4TSComponent
# Remove & recreate target component
# → NOW it works!
```

---

#### Rule 3: Build Only What You Changed

**TypeScript Changes**:
- Changed Web4TSComponent? → Build Web4TSComponent
- Changed target component? → Build target component
- Changed template? → Build Web4TSComponent, THEN remove/create target

**Shell Script Changes**:
- NO builds needed (shell is not compiled)
- BUT must sync template and apply to targets

---

#### Rule 4: Test at BOTH Levels

**Always test**:
1. ✅ Web4TSComponent's own CLI (direct)
2. ✅ Target component's CLI (delegation)

**Why**: Catches issues in:
- Direct method execution
- Delegation mechanism
- Context passing
- Template application

---

#### Rule 5: Document the Flow for Future Me

**Every fix should answer**:
1. Where was the bug? (Web4TSComponent vs target)
2. What file was changed? (exact path and lines)
3. Did it require a build? (which component?)
4. Did it require template sync? (remove/create?)
5. How was it tested? (exact commands)

**Format**: PDCA with Check section documenting verification!

## Summary: Multi-Component Development Model

### The Mental Model

```
┌─────────────────────────────────────────────────────┐
│ Web4TSComponent (Infrastructure)                    │
│ - DefaultCLI.ts (inherited by all)                  │
│ - DefaultWeb4TSComponent.ts (delegated to)          │
│ - Templates (blueprints for new components)         │
│ - Shell scripts (source + templates)                │
└─────────────────────────────────────────────────────┘
                        │
                        │ creates
                        ↓
┌─────────────────────────────────────────────────────┐
│ IdealMinimalComponent (Generated)                   │
│ - CLI inherits from DefaultCLI                      │
│ - Delegates to Web4TSComponent                      │
│ - Has own domain logic                              │
│ - Shell scripts copied from templates               │
└─────────────────────────────────────────────────────┘
```

### The Fix Flow

```
1. DIAGNOSE → Where? (Decision tree)
2. FIX      → Apply change in correct location
3. BUILD    → Only what changed (TypeScript)
4. APPLY    → Remove/create if template, skip if inheritance
5. TEST     → BOTH Web4TSComponent AND target
6. DOCUMENT → PDCA with verification
```

### The Golden Question

**"Do I need to remove/recreate the target component?"**

**YES if**:
- ✅ Fixed a template (`.template` file)
- ✅ Want to apply ALL latest fixes at once
- ✅ Component is test/demo only (easy to recreate)

**NO if**:
- ❌ Fixed `DefaultCLI.ts` or `DefaultWeb4TSComponent.ts` (inheritance)
- ❌ Component has valuable work (use manual sync)
- ❌ Only changed Web4TSComponent's own logic
