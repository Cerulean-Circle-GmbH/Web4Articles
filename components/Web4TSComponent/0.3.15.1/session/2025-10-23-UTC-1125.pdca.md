### **Root Cause Analysis**

**Why does old version work from test/data?**
```typescript
// Old version testSelective method (0.3.13.2)
const testDir = path.join(process.cwd(), 'test');
// When in test/data, process.cwd() = .../test/data
// testDir = .../test/data/test → symlink to actual tests ✅
```

**Why does new version fail from project root?**
```typescript
// New version testSelective method (0.3.15.1) - SAME CODE
const testDir = path.join(process.cwd(), 'test');
// When in project root, process.cwd() = .../Web4Articles
// testDir = .../Web4Articles/test → doesn't exist ❌
```

**The Issue:**
- Both versions use `process.cwd() + '/test'`
- Old version works because in isolation, `process.cwd()` is `test/data`
- New version expects to be run from component directory
- This is NOT a regression - it's **expected behavior** for component-centric commands

### **Behavioral Insights**

**Old Version (0.3.13.2) Isolation Success:**
1. ✅ Symlink trick: `test/data/test` → copied component's test directory
2. ✅ This makes old code (`process.cwd() + '/test'`) work perfectly
3. ✅ The piggy hack solved a real architectural challenge!

**New Version (0.3.15.1) Design:**
1. 🎯 Component-centric: Commands assume you're in component context
2. 🎯 This is actually **correct** for component commands
3. 🤔 But less flexible than auto-discovery approach

### **UX Comparison**

**Old UX (0.3.13.2 in isolation):**

### **Web4 Architecture Principle Violation?**

**Question:** Should component commands work from **any** directory?

**Web4 Answer:** Components should **self-discover** their context!
- ✅ Component should find its own location via `findProjectRoot()` + introspection
- ✅ Component should NOT require user to `cd` to specific directory
- ❌ Current implementation violates "empty constructor + self-discovery" principle

## **🎯 ACT**

### **Implementation Complete** ✅

**Web4 Pattern Applied:**
```typescript
// BEFORE (CMM2 - relied on process.cwd()):
let testDir: string;
if (process.cwd().endsWith('/test/data')) {
  testDir = path.join(process.cwd(), '../../test');
} else if (context) {
  testDir = path.join(this.resolveComponentPath(context.component, context.version), 'test');
} else {
  testDir = path.join(process.cwd(), 'test'); // ❌ Fails from project root!
}

// AFTER (CMM3 - uses model.targetDirectory):
let testDir: string;
if (context) {
  // When loaded with .on() command - test the target component
  testDir = path.join(this.resolveComponentPath(context.component, context.version), 'test');
} else {
  // No context - testing SELF (this component)
  // Use targetDirectory (which is projectRoot by default, or test/data in isolation)
  const componentRoot = path.join(
    this.model.targetDirectory, // ✅ Web4 pattern!
    'components',
    this.model.component,
    this.model.version
  );
  testDir = path.join(componentRoot, 'test');
}
```

## **📝 FINAL UPDATE: Describe Filtering Fixed**

**Additional Bug Fix (Commit `68343444`):**

**Problem:** `web4tscomponent test describe 24` returned empty
**Root Cause:** `HierarchicalCompletionFilter` checked for pattern `'[a-z]\\)'` in source, but actual pattern `/([a-z])\)/` has capture group parentheses
**Solution:** Check captured token content instead: `!fullToken.match(/^\d/) && fullToken.match(/^[a-z]$/)`
**Result:** Progressive filtering works for describe blocks too!

**Verification:**
```bash
$ web4tscomponent test describe 2
# Shows files 2, 20, 21, 22, 23, 24, 25 ✅

$ web4tscomponent test describe 24
# Shows only file 24's describe blocks ✅
```

**Key Insight:** The OLD completion code (in `DefaultCLI.getTestDescribeReferences`) had the CORRECT filtering logic manually implemented. By examining it, we found the bug was in the DRY utility class itself. Fix now benefits ALL uses of HierarchicalCompletionFilter.
