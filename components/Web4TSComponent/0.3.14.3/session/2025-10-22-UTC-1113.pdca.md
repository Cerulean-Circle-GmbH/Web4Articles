### **Step 1: TSCompletion.ts Architecture Analysis**

**File:** Lines 1-998 (complete review)

**What TSCompletion Provides:**
1. **AST Parsing Methods:**
   - `extractJsDocText()` - Extract main JSDoc comment
   - `extractParamJsDoc()` - Extract @param tags
   - `extractEnhancedJsDocText()` - Enhanced comment detection
   - `parseCliAnnotations()` - Extract @cli* annotations

2. **Discovery Methods:**
   - `getProjectSourceFiles()` - Discover all TS files in layers 1-5
   - `getClasses()` - Discover all class names
   - `getClassMethods(className)` - Discover methods (supports comma-separated classes)
   - `getMethodParameters(className, methodName)` - Extract parameters

3. **Enhanced Parameter Analysis:**
   - `getEnhancedMethodParameters()` - Extract params with type info, union types, defaults, required/optional
   - `isUnionType()` / `extractUnionTypes()` - Parse union types
   - `extractCliAnnotations()` - Get @cliHide, @cliSyntax, @cliOptional, etc.
   - `extractCliValues()` - Get @cliValues enum values

4. **Completion Logic:**
   - `complete(args[])` - Main completion algorithm (callback detection, parameter completion)
   - `getParameterCallback()` - Find callback method for parameter
   - Returns `__CALLBACK__:methodName` for dynamic values

5. **Documentation Methods:**
   - `getClassDoc()` - Get class JSDoc
   - `getMethodDoc()` - Get method JSDoc  
   - `getParamDoc()` - Get parameter JSDoc
   - `isMethodHidden()` - Check @cliHide

### **Step 2: DefaultCLI.ts Completion Pattern Analysis**

**Key Completion Methods:**

1. **`completeParameter(callbackName, ...contextArgs)`** (lines 1425-1442)
   - Entry point for bash callback execution
   - Calls callback method: `(this as any)[callbackName](contextArgs)`
   - Uses `formatCompletionOutput()` for DISPLAY/WORD protocol
   - Constructs `commandContext` from `process.env.WEB4_CLI_NAME`

2. **`formatCompletionOutput(values, commandContext)`** (lines 1325-1417)
   - DRY helper for DISPLAY/WORD protocol
   - Detects complex format (numbered refs, spaces)
   - Strips ANSI from WORD lines
   - Adds colored prompt echo (if WEB4_CLI_NAME set)
   - ONE `console.log()` for efficiency

3. **Parameter Completion Callbacks:**
   - `whatParameterCompletion()` → ['method', 'parameter']
   - `filterParameterCompletion()` → Delegates to `completionNameParameterCompletion()`
   - `completionNameParameterCompletion()` → Main logic for method/parameter listing

4. **`completionNameParameterCompletion(currentArgs)`** (lines 1547-1743)
   - Reads `what` value from `currentArgs[1]`
   - If `what === 'parameter'`: Lists `*ParameterCompletion` methods
   - If `what === 'method'`: Uses `methodSignatures` to list methods
   - Single match: Returns method signature + documentation
   - Multi-match: Returns numbered list

### **Step 3: Collaboration Analysis**

**Current Pattern:**

```
┌──────────────────────────────────────────────────┐
│ Bash Completion                                   │
│ - Calls: cli completion method <filter>          │
│ - Or: cli completeParameter callback args        │
└──────────────────┬───────────────────────────────┘
                   │
┌──────────────────▼───────────────────────────────┐
│ DefaultCLI                                        │
│ ├─ completeParameter(callback, ...args)          │
│ │  └─ Calls: this[callback](args)                │
│ │     └─ formatCompletionOutput(values, context) │
│ │                                                 │
│ ├─ completionNameParameterCompletion(args)       │
│ │  ├─ Uses: this.methodSignatures (own data)     │
│ │  └─ Calls: TSCompletion.getEnhancedMethodParameters() │
│ │                                                 │
│ └─ formatCompletionOutput(values, context)       │
│    └─ ONE place for DISPLAY/WORD protocol        │
└──────────────────┬───────────────────────────────┘
                   │
┌──────────────────▼───────────────────────────────┐
│ TSCompletion (Static Utility)                    │
│ ├─ getEnhancedMethodParameters(class, method)    │
│ │  └─ AST parsing → param info                   │
│ │                                                 │
│ ├─ getParameterCallback(class, method, index)    │
│ │  └─ Find callback method name                  │
│ │                                                 │
│ ├─ getMethodDoc(class, method)                   │
│ │  └─ Extract JSDoc documentation                │
│ │                                                 │
│ └─ isMethodHidden(class, method)                 │
│    └─ Check @cliHide annotation                  │
└───────────────────────────────────────────────────┘
```

**What Works Well:**
1. ✅ **Clear separation:** TSCompletion = AST parsing, DefaultCLI = output formatting
2. ✅ **DRY achieved:** `formatCompletionOutput()` is ONE place for DISPLAY/WORD
3. ✅ **Static utility pattern:** TSCompletion doesn't need state
4. ✅ **Callback discovery:** `getParameterCallback()` enables dynamic completion

**What Needs Optimization:**
1. ❌ **Duplication:** `completionNameParameterCompletion()` uses `this.methodSignatures` but TSCompletion has `getClassMethods()`
2. ❌ **Mixed concerns:** DefaultCLI calls TSCompletion for parameters but uses own `methodSignatures` for methods
3. ❌ **No caching:** TSCompletion re-parses AST on every call (expensive)
4. ❌ **Tight coupling:** `completionNameParameterCompletion()` knows about TSCompletion internals

## **🎯 ACT**

### **Optimization Insights for Spec**

#### **1. Current Collaboration (FOR IMMEDIATE FUTURE)**

**Bash → DefaultCLI → TSCompletion** pattern is correct and complete. No changes needed for current OOP redesign.

**Why:** 
- Clear responsibilities: TSCompletion = AST parsing, DefaultCLI = business logic + formatting
- DRY achieved: `formatCompletionOutput()` is central hub
- Extensible: New completion callbacks just implement method naming convention

#### **2. Future Optimizations (FOR LATER CMM4 ITERATIONS)**

**A) TSCompletion Method Discovery** (Low Priority)
- **Issue:** `completionNameParameterCompletion()` uses `this.methodSignatures` (instance data) instead of TSCompletion's `getClassMethods()` (shared utility)
- **Benefit:** Would enable completion discovery without CLI instance
- **Cost:** Requires refactoring `methodSignatures` initialization
- **Decision:** DEFER until needed

**B) TSCompletion AST Caching** (Medium Priority)
- **Issue:** Every `getEnhancedMethodParameters()` call re-parses AST (~200 methods × N calls)
- **Benefit:** 10x+ speed improvement for large method lists
- **Cost:** Memory overhead, cache invalidation logic
- **Decision:** MEASURE first (is it actually slow?), then optimize

**C) Unified Method Source** (Low Priority)
- **Issue:** Methods discovered via `discoverMethods()` (runtime reflection) AND `TSCompletion.getClassMethods()` (AST parsing)
- **Benefit:** Single source of truth
- **Cost:** Must handle both compiled and source modes
- **Decision:** DEFER - current dual approach handles edge cases well

**D) Completion Context Model** (Current Work!)
- **Issue:** Bash passes raw arrays, TypeScript reconstructs context
- **Benefit:** Scenario-based model with proper OOP
- **Current:** THIS IS THE NEW ARCHITECTURE WE'RE DESIGNING!
- **Impact:** Will REPLACE bash array passing with Scenario JSON exchange

## TSCompletion Integration

### Current Collaboration Pattern

DefaultCLI and TSCompletion have clear separation:
- **TSCompletion:** Static utility for AST parsing (getEnhancedMethodParameters, getMethodDoc, getParameterCallback)
- **DefaultCLI:** Business logic + formatting (formatCompletionOutput, completeParameter callbacks)

### Methods Using TSCompletion

1. **completionNameParameterCompletion()**
   - Calls: `TSCompletion.getEnhancedMethodParameters()` for parameter info
   - Calls: `TSCompletion.getMethodDoc()` for documentation
   - Uses: `this.methodSignatures` for method discovery (instance data)

2. **completeParameter()**
   - Discovered by: `TSCompletion.getParameterCallback()`
   - Executes: callback method on CLI instance
   - Formats: via `formatCompletionOutput()`

### Future OOP Integration

When migrating to Scenario-based model:
- **TSCompletion remains static utility** (no change)
- **DefaultCLI uses TSCompletion to populate CLIModel** (new!)
- **Bash receives complete model, modifies only bash fields** (decoupling)

Example:
```typescript
async getCompletionScenario(): Promise<void> {
  // Use TSCompletion to discover method info
  const methods = TSCompletion.getClassMethods(this.componentClass.name);
  const methodDocs = methods.map(m => ({
    name: m,
    doc: TSCompletion.getMethodDoc(this.componentClass.name, m),
    params: TSCompletion.getEnhancedMethodParameters(this.componentClass.name, m)
  }));
  
  const scenario: Scenario<CLIModel> = {
    ior: { uuid: randomUUID(), component: "CLI" },
    model: {
      completionMethods: methodDocs,
      // ... other fields
    }
  };
  
  console.log(JSON.stringify(scenario));
}
