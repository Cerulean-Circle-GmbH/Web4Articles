## 🎯 **Plan: The Vision**

### **Problem Statement**
The promotion workflow had a critical flaw: after creating a new version (e.g., `0.3.5.1` (dev) → `0.3.5.2` (test)), tests continued running on the OLD version (`0.3.5.1`) instead of automatically switching to the NEW version (`0.3.5.2`).

This meant:
- ❌ Developer had to manually `cd ../0.3.5.2`
- ❌ Easy to forget and test the wrong version
- ❌ Promotion workflow was incomplete and manual
- ❌ No automatic progression through the stages

### **Root Cause Analysis**
The `handleDevToTest()` and `handleCreateFirstDev()` methods were creating new versions but NOT switching the execution context to test those new versions. The workflow stopped at version creation instead of continuing to test the newly created version.

### **Desired Outcome**
A **fully automatic** promotion workflow where:
1. Running `npm test` on `0.3.5.1` (dev) automatically:
   - Creates `0.3.5.2` (test)
   - **Switches to `0.3.5.2`** 
   - Runs tests on `0.3.5.2`
   - If 100% pass → promotes to `0.3.6.0` (prod)
   - Creates `0.3.6.1` (dev) for next cycle

2. External component tests (via `.on()` context) continue to work as before (manual version control by the test)

3. Zero manual intervention required for the entire promotion cycle

### **Success Criteria**
- ✅ 100% test coverage (143/143 tests passing)
- ✅ Automatic version switching for Web4TSComponent self-testing
- ✅ Manual version control preserved for external component testing
- ✅ Full promotion cycle: dev → test → prod → new dev
- ✅ Real production promotion proof (not just test simulation)

### **Phase 3: Dual Workflow Solution**
**Breakthrough Insight:** Web4TSComponent has TWO distinct testing scenarios:

1. **Self-testing (no context):** `npm test` from `0.3.5.1/` should auto-switch to newly created versions
2. **External testing (with context):** Tests using `.on(ComponentName, version)` control their own version switching

**Solution:** Conditional auto-switching based on component name and context:

```typescript
private async handleDevToTest(componentName: string, currentVersion: string): Promise<void> {
  console.log(`\n🧪 Creating test version from ${currentVersion}...`);
  
  try {
    // Create nextBuild version (increment build number)
    const testVersion = await this.createNextBuildVersion(componentName, currentVersion);
    
    // Set as test
    await this.createSemanticLink(componentName, 'test', testVersion);
    
    console.log(`\n✅ Stage 1 complete: ${currentVersion} (dev) → ${testVersion} (test)`);
    
    // CRITICAL: Only auto-switch for Web4TSComponent's SELF-testing (no context)
    // For other components (with context), the caller controls version switching
    if (componentName === 'Web4TSComponent' && !this.getComponentContext()) {
      console.log(`🔄 Switching to ${testVersion} to run tests...`);
      
      // Use execSync to run npm test in the new version's directory
      // (Can't use .on() because that would trigger recursion safety check)
      const componentPath = this.resolveComponentPath(componentName, testVersion);
      console.log(`🧪 Now running tests on ${testVersion} (test version)...`);
      
      try {
        execSync('npm test', {
          cwd: componentPath,
          stdio: 'inherit',
          encoding: 'utf-8'
        });
      } catch (error) {
        // Tests failed - this is OK, just don't promote
        console.log(`⚠️  Tests failed on ${testVersion} - will retry after fixes`);
      }
    } else {
      console.log(`📊 Next step: Manually switch to ${testVersion} and run tests for Stage 2`);
    }
    
  } catch (error) {
    console.error(`❌ Stage 1 failed: ${(error as Error).message}`);
    throw error;
  }
}
```

**Key Design Decisions:**
- Use `execSync('npm test', { cwd: componentPath })` instead of `.on()` + `.test()` to avoid recursion safety check
- Only auto-switch when `componentName === 'Web4TSComponent'` AND `!this.getComponentContext()`
- For external components, print a message but let the caller control version switching

## 🎯 **Act: Lessons Learned & Next Steps**

### **Key Insights**

1. **🎯 Dual Workflow Pattern**
   - Self-testing components need automatic version switching
   - External component testing needs manual control
   - Both can coexist with conditional logic based on context

2. **🔄 Recursion Prevention via execSync**
   - Cannot use `.on()` + `.test()` for self-testing (triggers recursion check)
   - `execSync('npm test', { cwd: path })` provides clean separation
   - Each directory's `npm test` runs independently

3. **📊 Stage-Based Promotion**
   - Stage 0: prod → dev (first test run on prod version)
   - Stage 1: dev → test (ANY npm test on dev, regardless of pass/fail)
   - Stage 2: test → prod (ONLY on 100% test success on test version)
   - Post-Stage 2: prod → dev + test (create new dev cycle)

4. **🧪 Test Isolation**
   - Tests in `test/data` correctly isolated from production
   - No pollution of production environment during test runs
   - Clean separation of concerns
