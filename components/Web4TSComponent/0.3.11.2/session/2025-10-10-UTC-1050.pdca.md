## **🔍 PLAN**

### **Problem Statement**

**Current Behavior:**
```bash
# User types:
web4tscomponent links <Tab>

# TSCompletion returns parameter NAME:
action

# User expects parameter VALUES:
fix verify show list
```

**Root Cause:** TSCompletion doesn't distinguish between:
1. **Required positional parameters** (need parameter name for help)
2. **Optional parameters with default values** (need parameter values for completion)

### **The Completion Ambiguity Problem**

**Scenario 1: Required Parameters (need name)**
```typescript
async create(name: string, version: string): Promise<void>
```
```bash
web4tscomponent create <Tab>
# Should show: name (parameter name as hint)
# User then types: MyComponent
```

**Scenario 2: Optional Parameters (need values)**
```typescript
async links(action: string = ''): Promise<void>
```
```bash
web4tscomponent links <Tab>
# Currently shows: action (parameter name - WRONG!)
# Should show: fix verify show list (parameter values - RIGHT!)
```

### **Current TSCompletion Logic (Simplified)**

```typescript
// In TSCompletion.ts line 302-310
if (subMethods[0] === methodPrefix) {
  // Method name is complete - what to return?
  const params = TSCompletion.getMethodParameters(className, methodPrefix);
  if (params.length > 0 && params[0] === 'action') {
    // HARDCODED: Return action VALUES
    return ['', 'fix', 'verify', 'show', 'list'];
  }
  // Default: return parameter NAMES
  return params;
}
```

**The hardcoded check is a CODE SMELL!**

## **🎯 Architecture Analysis**

### **Option 1: Named Parameters (User Suggestion)**

**Syntax:**
```bash
web4tscomponent links action=fix
web4tscomponent create name=MyComponent version=1.0.0.0
```

**Pros:**
✅ Explicit - always clear what parameter is what  
✅ Order-independent - can swap parameters  
✅ Self-documenting - readable in logs/history  
✅ Easy completion - always show available values after `=`

**Cons:**
❌ More verbose - extra typing  
❌ Breaking change - ALL existing commands break  
❌ Requires parser refactoring in DefaultCLI  
❌ Non-standard for CLI tools (most use positional)

**Impact:**
- **DefaultCLI.executeDynamicCommand()** needs complete rewrite
- All existing scripts/tests break
- Generated components need updated templates
- **MASSIVE REFACTORING**

### **Option 2: Positional + Smart Completion (Incremental)**

**Syntax (unchanged):**
```bash
web4tscomponent links fix          # Positional (current)
web4tscomponent create MyComponent 1.0.0.0
```

**Completion Enhancement:**
- TSCompletion detects optional parameters with `@cliDefault` annotation
- Returns VALUES instead of NAMES for optional params
- Uses `actionParameterCompletion()` callback for dynamic values

**Pros:**
✅ No breaking changes - backward compatible  
✅ Incremental enhancement  
✅ Standard CLI pattern (like git, docker, npm)  
✅ Leverages existing parameter completion infrastructure

**Cons:**
❌ Completion logic more complex (context-aware)  
❌ Positional order still matters  
❌ Less explicit than named params

**Impact:**
- Enhance TSCompletion to detect optional params
- No DefaultCLI parser changes
- No breaking changes
- **MINIMAL REFACTORING**

### **Option 3: Hybrid Approach (Future)**

**Syntax:**
```bash
# Both supported:
web4tscomponent links fix                    # Positional (short)
web4tscomponent links action=fix             # Named (explicit)
web4tscomponent create MyComponent 1.0.0.0   # Positional
web4tscomponent create name=MyComponent version=1.0.0.0  # Named
```

**Pros:**
✅ Best of both worlds  
✅ Backward compatible (if done right)  
✅ Power users can use named, beginners use positional

**Cons:**
❌ Most complex to implement  
❌ Parser needs to handle both styles  
❌ Potential confusion about which to use

**Impact:**
- Parser in DefaultCLI needs enhancement (not rewrite)
- Completion needs to detect `=` in current word
- **MODERATE REFACTORING**

## **🎯 Recommended Approach**

### **Phase 1: Option 2 (NOW) - Smart Positional Completion**

**Implement:**
1. Enhance TSCompletion to detect `@cliOptional` and `@cliDefault` annotations
2. When method has optional param, return VALUES not NAMES
3. Use callback to `actionParameterCompletion()` for dynamic values
4. Remove hardcoded `if (params[0] === 'action')` check

**Changes Required:**

**File:** `TSCompletion.ts` (line 302-310)
```typescript
if (subMethods[0] === methodPrefix) {
  const params = TSCompletion.getMethodParameters(className, methodPrefix);
  if (params.length > 0) {
    // Check if first param is optional with default
    const paramInfo = TSCompletion.getEnhancedMethodParameters(className, methodPrefix)[0];
    if (paramInfo && !paramInfo.required && paramInfo.default !== undefined) {
      // Optional param - try to get VALUES from completion callback
      const completionMethod = `${params[0]}ParameterCompletion`;
      // Return callback name as hint to bash function
      return [`__CALLBACK__:${completionMethod}`];
    }
  }
  // Required params - return parameter NAMES as hints
  return params;
}
```

**File:** `source.env` (bash completion)
```bash
local out=$(NODE_NO_WARNINGS=1 node --loader ts-node/esm "$tsc" "${completeArgs[@]}" 2>>"$logfile" || true)

# Check if TSCompletion returned a callback hint
if [[ "$out" == __CALLBACK__:* ]]; then
    local callback="${out#__CALLBACK__:}"
    # Call TypeScript to execute the completion callback
    out=$(web4tscomponent __completeParameter "$callback" "${args[@]}" 2>>"$logfile" || true)
fi
```

**File:** `DefaultCLI.ts` (new hidden method)
```typescript
/**
 * Execute parameter completion callback
 * @cliHide
 */
async __completeParameter(callbackName: string, ...args: string[]): Promise<void> {
  const component = this.getComponentInstance();
  if (typeof (component as any)[callbackName] === 'function') {
    const values = await (component as any)[callbackName](args);
    console.log(values.join(' '));
  }
}
```

**Risk:** LOW

## **💫 EMOTIONAL REFLECTION**

**Key Insight:** The completion ambiguity (names vs values) reveals a deeper architectural question: How explicit should CLIs be?

Web4's principle of "Simplicity as the highest art of complexity" suggests:
- **Start simple** (positional params - Phase 1)
- **Add power** (named params - Phase 2)
- **Never break** (backward compatibility always)

The debug logging proved invaluable - it instantly revealed the exact issue (suffix vs full word). This is CMM3: systematic diagnosis over guessing.
