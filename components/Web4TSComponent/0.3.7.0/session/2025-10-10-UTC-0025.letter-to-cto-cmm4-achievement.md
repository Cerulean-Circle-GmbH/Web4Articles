## 🎯 The Three Turning Points

### **1. "You're Running Tests on the Wrong Version"**

**What Happened:**  
I was confidently running tests on `0.3.6.3`, making changes, and declaring success. But the promotion workflow created `0.3.6.4` and I never switched to it. I was testing yesterday's code while today's code sat untested.

**What I Learned:**  
**Context switching isn't just a feature - it's a necessity.** When a promotion creates a new version, the system *must* automatically switch to that version and continue testing there. Otherwise, you're building a house of cards where each floor is disconnected from the ones below.

**The Pattern I Discovered:**
```typescript
// After Stage 1 creates test version:
if (currentVersion === semanticLinks.dev) {
  const newTestVersion = updatedLinks.test;
  if (newTestVersion && newTestVersion !== currentVersion) {
    // 🔄 CRITICAL: Switch context and continue testing
    await this.on('Web4TSComponent', newTestVersion);
    execSync('npm test', { cwd: newTestPath, stdio: 'inherit' });
  }
}
```

This isn't complexity for complexity's sake - it's the *minimum necessary complexity* to ensure correctness.

---

### **2. "Find the Project Root Once, Then Use It Everywhere"**

**What Happened:**  
I was calculating relative paths over and over, each time with subtle variations. Sometimes using `process.cwd()`, sometimes using `__dirname`, sometimes using complex symlink resolution. It was fragile, inconsistent, and impossible to debug.

**What I Learned:**  
**Simplicity in use requires clarity in storage.** The human frustration: "Why does this keep breaking?" The answer: Because I kept *rediscovering* the project root instead of *remembering* it.

**The Pattern I Applied:**
```typescript
constructor() {
  const discoveredRoot = this.findProjectRoot();
  this.model = {
    uuid: crypto.randomUUID(),
    projectRoot: discoveredRoot,        // Found ONCE
    targetDirectory: discoveredRoot,    // Can be overridden (test isolation)
    // ... rest of model
  };
}

// Later, everywhere:
const absolutePath = path.join(this.model.projectRoot, 'components', componentName);
// No more relative path calculations! No more cwd() confusion!
```

This is what you mean by "single source of truth." It's not about databases or architecture - it's about *deciding once and remembering forever*.

## 🔗 The Dual Link Crisis - CMM4 → CMM2 → CMM3

**The Problem:** I failed to provide correct dual links 10 times in a row.

**The Root Cause:** I didn't understand that dual links have **two different formats** depending on context:

### **Format 1: In Markdown Files**
```markdown
**Label:** [GitHub](url) | [§/path/from/root](../../../../relative/path)
```
- Display text: `§/full/path/from/project/root`
- Link URL: Relative path from the markdown file to target

### **Format 2: In Chat/Transient Context**
```markdown
**Label:** [GitHub](url) | [§/path/from/root](file:///absolute/path)
```
- Display text: `§/full/path/from/project/root` (same)
- Link URL: Absolute `file://` URL (because chat has no file context)

**Why I Failed 10 Times:**
1. ❌ Hallucinated format without checking examples
2. ❌ Didn't read `scripts/fix.dual.links` when told to
3. ❌ Confused markdown file context with chat context
4. ❌ Kept trying relative paths in chat where they don't resolve
5. ❌ Lost CMM4 badge → demoted to CMM2
6. ✅ Finally read the documentation
7. ✅ Understood the two contexts
8. ✅ Earned CMM3 back

**The Solution (Documented Forever):**

**When providing dual links in chat:**
```markdown
[GitHub](commit-sha-url) | [§/path](file:///absolute/path)
```

**When providing dual links in markdown files:**
```markdown
[GitHub](commit-sha-url) | [§/path](../../../relative/path)
```

**How to Never Fail Again:**
1. Read `scripts/fix.dual.links` (lines 45-46 show the standard)
2. Check if context is **chat** (use absolute) or **file** (use relative)
3. Test the link before providing it
4. Never trust memory - always grep for examples
