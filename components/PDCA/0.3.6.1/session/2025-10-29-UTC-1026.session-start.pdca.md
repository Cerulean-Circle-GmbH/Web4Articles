### **Critical Issue Discovered**

#### **Symptom**
```bash
$ pdca links
❌ CLI Error: Cannot read properties of undefined (reading 'targetDirectory')
```

#### **Root Cause Analysis**
1. **Error occurs in:** `DefaultPDCA.ts` → `getWeb4TSComponent()` → delegates to Web4TSComponent
2. **Missing initialization:** `DefaultWeb4TSComponent` constructor initializes `model.targetDirectory` and `model.projectRoot`
3. **PDCA model missing fields:** `PDCAModel.interface.ts` does not extend fields from Web4TSComponent's model
4. **Delegation breaks:** When PDCA creates `new DefaultWeb4TSComponent()` and calls `web4ts.on()`, the Web4TSComponent expects its own model fields

#### **Affected Scope**
- ❌ All PDCA CLI methods that delegate to Web4TSComponent (links, test, build, etc.)
- ❌ Both 0.3.5.1 and 0.3.6.1 versions affected (merge introduced regression)
- ⚠️ PDCA component is completely non-functional

### **Implementation Plan**

#### **Option 1: Add Missing Fields to PDCAModel (Recommended)**
Add `projectRoot` and `targetDirectory` to `PDCAModel.interface.ts` and initialize them in `DefaultPDCA` constructor.

**Pros:**
- Follows same pattern as Web4TSComponent
- Clean separation of concerns
- Enables PDCA to work standalone

**Cons:**
- Adds fields that PDCA doesn't directly use

#### **Option 2: Set targetDirectory After Web4TSComponent Creation**
In `getWeb4TSComponent()`, set the targetDirectory explicitly after instantiation.

**Pros:**
- Minimal change
- No model interface changes

**Cons:**
- Fragile delegation pattern
- Tight coupling

#### **Recommended:** Option 1 for CMM3 compliance and maintainability
