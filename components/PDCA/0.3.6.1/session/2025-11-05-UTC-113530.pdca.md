## **📊 SUMMARY**

**CRITICAL BUG:** `rename now` permanently destroys the original creation timestamp - `rename creationDate` cannot restore it!

**User's Experience:**
```
1. File created: 2025-11-05-UTC-113203.pdca.md (11:32:03)
2. User runs: pdca rename now
   Result: 2025-11-05-UTC-113324.pdca.md (11:33:24)
   ❌ ORIGINAL TIME LOST (11:32:03 is gone!)

3. User runs: pdca rename creationDate (to restore original)
   Result: Nothing happens (silent)
   Why: Git log shows creation as 11:33:24 (the rename commit)
        Original 11:32:03 is permanently lost!
```

**Root Cause:** Our recent fix removed `--follow` from `rename creationDate` to fix the "3 months ago" bug. But this created a NEW bug:
- Without `--follow`, git log only sees the CURRENT file's history
- After `rename now`, the current file's "creation" is the rename commit
- The ORIGINAL creation timestamp is lost forever

**Impact:**
- **Data Loss:** Original creation timestamps permanently destroyed
- **No Recovery:** `rename creationDate` can't restore what's lost
- **Silent Failure:** No warning that original timestamp is being destroyed
- **Broken Workflow:** `rename now` → `rename creationDate` doesn't work

**The Dilemma:**
- **With `--follow`:** Gets wrong dates (ancestor files from months ago) ❌
- **Without `--follow`:** Loses original dates after `rename now` ❌

## **📋 PLAN**

**Objective:** Fix `rename creationDate` to preserve original creation time through renames, while avoiding ancestor file dates

**Requirements Traceability:** User bug report - original timestamp lost after `rename now`

### **Proposed Solutions**

**Option A: Smart `--follow` with Depth Limit**
- Use `--follow` but only follow 1-2 renames back
- Stops before reaching ancestor files from months ago
- Preserves original creation through recent renames
- **Pros:** Simple, uses existing git features
- **Cons:** Hard to determine "safe" depth, might still get wrong dates

**Option B: Parse Filename for Original Timestamp**
- Extract timestamp from CURRENT filename as "original"
- Use that as the creation date
- **Pros:** Simple, no git log needed
- **Cons:** Assumes filename is always correct (circular logic)

**Option C: Use `git log --follow` with Smart Filtering**
- Get full history with `--follow`
- Filter out commits older than X days (e.g., 7 days)
- Use the oldest commit within the time window
- **Pros:** Balances both needs
- **Cons:** Arbitrary time window, complex logic

**Option D: Track Original Creation in Git Notes** ⭐ **RECOMMENDED**
- When file is first created, store original timestamp in git notes
- On rename, preserve the git note
- `rename creationDate` reads from git note, not commit history
- **Pros:** Explicit, accurate, survives renames
- **Cons:** Requires infrastructure for git notes

**Option E: Hybrid - `--follow` with Rename Detection**
- Use `git log --follow` to get full history
- Detect the FIRST commit that's NOT a rename
- Use that as the true creation date
- **Pros:** Accurate, uses git semantics
- **Cons:** Complex parsing of commit messages

**Implementation: Git Notes for Original Creation Timestamp**

### **How Git Notes Work**

Git notes are like "sticky notes" attached to commits. They:
- Store metadata separately from commit messages
- Survive renames (can be copied to new commits)
- Don't modify commit history
- Are pushed/pulled separately (`git push origin refs/notes/*`)
