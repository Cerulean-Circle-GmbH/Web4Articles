**Root Cause Understanding:**
- **Primary:** Context-based assumption - inferred location from reading context instead of querying Decision 4a
- **Secondary:** Pattern repetition - same "think I know" assumption from previous PDCA, different dimension (location vs identity)
- **Meta:** RAG-like verification principle violation - applied context without querying selections

**Pattern Prevention Applied:**

**1. RAG-Like Verification Protocol:**

Before ANY action based on context:
```
STEP 1: Query explicit selections/requirements
  - "What did user select for Decision X?"
  - "What does requirement Y specify?"
  
STEP 2: Retrieve from correct source
  - User selections (highest priority)
  - Documented requirements (second priority)  
  - Context observations (lowest priority)

STEP 3: Verify retrieved matches need
  - "Does this selection apply to current task?"
  - "Is this the authoritative source?"

STEP 4: Apply verified information
  - Use selection/requirement as directive
  - Use context as supporting information
```

**2. Decision Verification Checklist:**

When starting any task:
- [ ] Query Decision 1 (Work Focus) - Does task match selected focus?
- [ ] Query Decision 2 (Role) - Am I operating in selected role?
- [ ] Query Decision 3 (Duration) - Does task fit session planning?
- [ ] Query Decision 4 (Location) - Am I creating artifacts in selected location?
- [ ] Query Decision 5 (Identity) - Am I using verified agent identity?

**Never assume any decision from context - always query selections**

**3. Location Verification Specifically:**

Before creating ANY file:
```bash
# Query Decision 4 selection
echo "Decision 4 selected: [query user selections]"

# Map to actual path
case "$DECISION_4" in
  "4a") LOCATION="scrum.pmo/roles/${ROLE}/pdca/" ;;
  "4b") LOCATION="scrum.pmo/project.journal/${SESSION}/" ;;
  "4c") LOCATION="scrum.pmo/sprints/${SPRINT}/" ;;
  "4d") LOCATION="components/${COMPONENT}/pdca/" ;;
esac

# Verify location exists or create
mkdir -p "$LOCATION"

# Create file in VERIFIED location
touch "${LOCATION}${FILENAME}"
```

**4. Context vs Selection Priority:**

| Information Type | Priority | Use For | Don't Use For |
|-----------------|----------|---------|---------------|
| **User Selections** | 1 (Highest) | Action directives | Supporting context only |
| **Requirements** | 2 (High) | Process compliance | Optional interpretation |
| **Context Observations** | 3 (Low) | Understanding background | Action decisions |

**Selection overrides context ALWAYS**

**Key Learnings:**

**1. RAG System Analogy is Perfect**

RAG systems don't assume from whatever document they're currently reading. They:
- Query for specific need
- Retrieve from authoritative source
- Apply retrieved information

Agents should work the same way with user selections.

**2. Context Informs, Selections Direct**

Context (breadcrumb trail location) helps UNDERSTAND the situation.
Selections (Decision 4a) DIRECT where to act.

Confusing these causes errors.

**3. Pattern Applies to ALL Decision Dimensions**

Same assumption pattern manifests across:
- Identity (Decision 5) - assumed agent name
- Location (Decision 4) - assumed from reading context
- Likely future: Focus, Role, Duration if not careful

**Systematic verification prevents ALL dimensions**

**4. "Older Context" Requires Extra Vigilance**

TRON's teaching: "starting in an older context" means reading historical session directory.

This makes context-based assumption MORE tempting because there's MORE context to assume from.

RAG-like verification becomes MORE critical, not less.
