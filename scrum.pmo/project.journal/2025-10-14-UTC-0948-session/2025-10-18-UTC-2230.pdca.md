## **⚡ ACT: Lessons Learned & Best Practices**

### **1. Default Value Completion Philosophy**

**Question:** Should default values appear in tab completions?

**Answer:** It depends on the semantic meaning:

| Parameter Type | Show Default? | Reason |
|---|---|---|
| **Implicit Behavior** | ❌ No | Default means "no override" (e.g., `scope='all'`) |
| **Explicit Choice** | ✅ Yes | Default is a valid option among many (e.g., `version='latest'`) |
| **Dynamic Value** | ✅ Yes | Default is computed/context-dependent (e.g., `targetDir='§'`) |

### **2. The `scope='all'` Case**

**Semantic Analysis:**
- `'all'` means "run everything" (no filtering)
- `'file'`, `'describe'`, `'itCase'` mean "filter to specific scope"
- User pressing TAB after `test` is looking for **filtering options**
- Not offering a filter = running all (implicit default)

**Conclusion:** `'all'` is not a "choice", it's the absence of a choice → hide from completions.

**What CMM4 Means:**

- **Quantitative Management:** User feedback quantifies quality
- **Predictable Quality:** Consistent UX patterns across all commands

**How This Fix Demonstrates CMM4:**

2. **User-Centric:** Reduces cognitive load
3. **Documentation:** Clear JSDoc explains the reasoning
4. **Testability:** Verifiable behavior change

### **4. Pattern for Future Parameters**

**Decision Tree:**
```
New parameter with default value?
  ├─ Default means "do nothing special"? → Hide from completions
  ├─ Default is one valid option among many? → Show in completions (maybe yellow)
  └─ Default is dynamically computed? → Show in completions (resolve at runtime)
```

**Examples:**
- `test <?scope:'all'>` → Hide `'all'` ✅
- `releaseTest <?versionPromotion:'nextPatch'>` → Show `'nextPatch'` (yellow) ✅
- `initProject <?targetDir:'§'>` → Show `'§'` (resolve to path) ✅
