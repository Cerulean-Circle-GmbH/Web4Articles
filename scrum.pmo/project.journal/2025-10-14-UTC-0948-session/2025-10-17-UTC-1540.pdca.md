### **Step 3: Design Component.interface.ts Base (✅ COMPLETE)**

**Core Principle:** Every Web4 component is a component with:
1. **Lifecycle:** init, process, toScenario
1. **Introspection:** getComponentContext, web4ts reference
1. **Type Safety:** Fluent `this` return type

**Proposed Design:**

```typescript
/**
 * Component.interface.ts - Base interface for ALL Web4 components
 * Every Web4 component must implement these fundamental methods
 * 
 * Purpose: Provides common contract for component lifecycle, introspection, and CLI integration
 */

import { Scenario } from './Scenario.interface.js';
import { Model } from './Model.interface.js';

/**
 * Base interface for all Web4 components
 * Ensures every component has fundamental lifecycle and introspection methods
 */
export interface Component<TModel extends Model = Model> {
  /**
   * Initialize component with scenario (Web4 pattern)
   * @param scenario Scenario containing component configuration and initial state
   * @returns this for method chaining
   */
  init(scenario: Scenario<TModel>): this;
  
  /**
   * Convert component state to scenario for persistence/transfer
   * @param name Optional scenario name
   * @returns Scenario representation of current component state
   */
  toScenario(name?: string): Promise<Scenario<TModel>>;
  
  /**
   * Process component logic (component-specific implementation)
   * @returns this for method chaining
   */
  process(...args: any[]): Promise<this> | this;
}

/**
 * Extended interface for components with Web4TSComponent delegation
 * All generated components get a web4ts reference for advanced features
 */
export interface ComponentWithWeb4TS<TModel extends Model = Model> extends Component<TModel> {
  /**
   * Web4TSComponent instance for delegation (DRY principle)
   * Provides access to hierarchical testing, comparison, tree view, etc.
   * @internal Used by CLI layer for completion callbacks
   */
  readonly web4ts: any; // Will be properly typed as Web4TSComponent once circular dep resolved
}
```

**Why Two Interfaces?**
1. `Component` - Minimal contract for ALL components
1. `ComponentWithWeb4TS` - For generated components with web4ts delegation

**Benefits:**
- ✅ Type-safe access to `component.web4ts` in DefaultCLI
- ✅ No more `(this as any)` casts
- ✅ Clear contract for all components
- ✅ Generic `TModel` supports any component model

## **🎯 ACT**

### **QA Decisions**

1. **Q:** Should we create Component.interface.ts as base for all components?
   **A:** YES. Provides type safety, eliminates ugly casts, establishes clear architectural contract.

1. **Q:** Should MethodSignature be moved to layer3?
   **A:** YES. Fixes architectural violation. Interfaces belong in layer3, not layer2.

1. **Q:** Should we use Component vs ComponentWithWeb4TS split?
   **A:** YES. Allows minimal components (Component) and full-featured generated components (ComponentWithWeb4TS) with delegation.

1. **Q:** What about circular dependencies (Component → Web4TSComponent → Component)?
   **A:** NOT an issue. Component.interface.ts doesn't import Web4TSComponent. Web4TSComponent extends Component. One-way dependency.

1. **Q:** Should existing components be updated immediately?
   **A:** OPTIONAL. New components get it automatically. Existing components can be migrated incrementally.

### **Lessons Learned**

1. **Layer Violations Cost:** MethodSignature in layer2 for years - technical debt compounds
1. **Type Safety Matters:** `(this as any)` casts hide architectural issues
1. **Base Interfaces Enable DRY:** Common contract eliminates duplication
1. **Generics Provide Flexibility:** `Component<TModel>` works for any component model
1. **Split Interfaces Scale:** Component vs ComponentWithWeb4TS allows minimal and full-featured variants
