## **📝 PLAN**

### **Context**

Web4Programmer (0.1.0.1) was created from outdated Web4TSComponent templates before:
1. DRY delegation pattern was implemented
1. `getWeb4TSComponent()` lazy initialization helper was added
1. Hierarchical test methods (`test file/describe/itCase`) were added to templates
1. 23 comprehensive completion discovery tests were created

**Goal:** Analyze differences between Web4TSComponent master (0.3.13.1) and Web4Programmer (0.1.0.1) to determine:
1. Which files are outdated
1. What functionality is missing
1. How to synchronize using DRY principles
1. Whether to upgrade in place or recreate

**Expected Output:**
1. Detailed file-by-file drift analysis
1. Missing functionality assessment
1. Recommended synchronization strategy
1. Step-by-step upgrade plan

  private model: Web4ProgrammerModel;
  private _web4ts?: any; // ✅ ADD: Web4TSComponent instance for delegation

  // ✅ ADD: Lazy initialization helper
  private async getWeb4TSComponent(): Promise<any> {
    if (this._web4ts) return this._web4ts;
    // [~30 lines: path resolution + import + instantiation + 'on' context]
    return this._web4ts;
  }

  // ✅ UPDATE: test() signature and delegation
  async test(scope: string = 'all', ...references: string[]): Promise<this> {
    // Detect hierarchical test mode
    const selectiveScopes = ['file', 'describe', 'itCase'];
    if (selectiveScopes.includes(scope)) {
      const web4ts = await this.getWeb4TSComponent();
      await web4ts.test(scope, ...references);
      return this;
    }

  }

1. **Q:** Can Web4Programmer use hierarchical test commands natively?

1. **Q:** Can we use `web4tscomponent on Web4Programmer` as a workaround?
   **A:** ✅ YES. All modern features work via delegation. But native calls should also work (DRY principle).

## **🎯 ACT**

### **QA Decisions**

1. **Q:** Should we upgrade Web4Programmer in place or recreate it?
   **A:** UPGRADE IN PLACE. Web4Programmer has 4 session PDCAs and custom business logic. Recreating would lose history and require significant rework.

1. **Q:** Do we copy the updated template code or apply delegation pattern?
   **A:** APPLY DELEGATION PATTERN. Following DRY principle from Bug 3 fix. Add `getWeb4TSComponent()` helper and update `test()` method signature.

1. **Q:** Should we add all missing methods (completion, tree, etc.)?
   **A:** NO. Only add delegation infrastructure. Future methods can be added as needed using the same pattern.

1. **Q:** How to handle the 232+ lines of auto-promotion code in test()?
   **A:** KEEP IT for `scope === 'all'`. Only delegate for `scope === 'file'/'describe'/'itCase'`. This maintains backward compatibility.

### **Recommended Synchronization Strategy**

#### **Option A: Manual Update (RECOMMENDED)**

**Pros:**
1. Preserves existing code and history
1. Surgical changes only where needed
1. Maintains session PDCAs
1. Tests existing functionality

**Cons:**
1. Manual work required
1. Must verify each change

**Steps:**
1. Add `private _web4ts?: any;` property to DefaultWeb4Programmer
1. Add `getWeb4TSComponent()` helper method (copy from template)
1. Update `test()` method signature: `async test(scope: string = 'all', ...references: string[])`
1. Add delegation logic at start of `test()` method
1. Build Web4Programmer
1. Test hierarchical commands: `web4programmer test file/describe/itCase`
1. Test full suite: `web4programmer test` or `web4programmer test all`
1. Create PDCA documenting changes
1. Commit with proper message

#### **Option B: Template Regeneration (NOT RECOMMENDED)**

**Pros:**
1. Guaranteed template alignment
1. Automated process

**Cons:**
1. ❌ Loses 4 session PDCAs
1. ❌ Loses custom business logic (create, process, format methods)
1. ❌ Requires manual restoration of custom code
1. ❌ Breaks version history

**Verdict:** Option A (Manual Update) is strongly preferred.

#### **Option C: Use needsUpgradeCheck/upgrade Methods**

Web4Programmer has these methods:
```typescript
async needsUpgradeCheck(): Promise<this>
async upgrade(successPromotion: string): Promise<this>
```

**Investigation Result:**
```bash
$ web4tscomponent on Web4Programmer 0.1.0.1 needsUpgradeCheck
❌ CLI Error: Unknown command: needsUpgradeCheck
# Method exists in Web4Programmer but not in Web4TSComponent!

$ web4programmer needsUpgradeCheck
❌ CLI Error: I need a component context first. 
   Please use "on <component> <version>" before checking upgrade needs.
# Method requires 'on' context, creating circular dependency
```

**Findings:**
1. `needsUpgradeCheck()` exists in Web4Programmer, not in Web4TSComponent
1. Method requires `on` context (expects to be called FROM Web4TSComponent ON another component)
1. Architectural mismatch: The upgraded component has the upgrade detector, but the upgrader (Web4TSComponent) doesn't call it
1. Conclusion: These methods are incomplete/experimental, NOT safe for production use

**Verdict:** Option C is NOT viable. Option A (Manual Update) remains the recommended approach.

### **Lessons Learned**

1. **Template Drift Detection:** Compare tool is invaluable for detecting outdated components created from old templates.
1. **Context-Aware Delegation:** The `web4tscomponent on Component version` pattern provides powerful emergency fallback when components are outdated.
1. **DRY Validation:** Components created before delegation pattern violate DRY by duplicating 232+ lines of test logic.
1. **Upgrade Paths:** Generated components need clear upgrade mechanisms. `needsUpgradeCheck()` and `upgrade()` methods are promising but untested.
