- `false` = showHidden (don't show dot-files)

### **Step 3b: View Another Component's Tree (Context-Aware)**
```bash
./web4tscomponent on Web4Programmer 0.1.0.1 tree
```

**❌ WRONG SYNTAX (I tried this!):**
```bash
./web4tscomponent on Web4TSComponent tree  # Missing version!
```

**✅ CORRECT PATTERN:**
```bash
# Format: on <component> <version> <command>
./web4tscomponent on Web4Programmer 0.1.0.1 tree
./web4tscomponent on Unit 0.3.0.5 tree 2
./web4tscomponent on MyComponent latest tree
```

**What It Shows:**
```
✅ Component context loaded: Web4Programmer 0.1.0.1
   Path: /path/to/Web4Programmer/0.1.0.1
📁 Tree structure for Web4Programmer 0.1.0.1:

├── src/
│   ├── sh/
│   └── ts/
├── test/
│   └── web4programmer.test.ts
└── package.json
```

**Key Observation:**
- NO `templates/` directory → Created from template, not generator
- Minimal `test/` → Only basic test file
- Simple structure → Consumer component, not infrastructure

**Why Context-Aware Matters:**
- Load component context with `on`
- Then use ANY command on that component
- Even if component doesn't have the command itself!
- Web4TSComponent becomes universal tool for all components

## **6. Complete Analysis Workflow**

**Purpose:** Systematic component analysis from discovery to verification

### **Scenario: Template Divergence Investigation**

**Context:** Updated DefaultCLI in master, created new component, another agent fixed something.

**Step-by-Step Workflow:**

#### **Phase 1: Identify the Change**
```bash
# What changed?
git log --oneline -5
# Shows: Recent commits to DefaultCLI.ts
```

#### **Phase 2: Test the Master**
```bash
cd components/Web4TSComponent/0.3.13.1

# Find the test file
./web4tscomponent completeParameter referencesParameterCompletion test file
# Output: 3: web4tscomponent.completion-discovery.test.ts

# Run targeted tests
./web4tscomponent test file 3
# Result: 23/23 tests passing
```

#### **Phase 3: Compare Components**
```bash
# Compare master with deployed
./web4tscomponent compare "Web4TSComponent 0.3.13.1, Web4Programmer 0.1.0.1"

# Key finding:
# src/ts/layer2/DefaultCLI.ts: 🟩 Identical (after fix!)
```

#### **Phase 4: Analyze Structure**
```bash
# Master structure
./web4tscomponent tree 2 false
# Shows: templates/, test/, session/, comprehensive

# Deployed structure
./web4tscomponent on Web4Programmer 0.1.0.1 tree
# Shows: NO templates/, minimal test/, created from template
```

#### **Phase 5: Check Template Drift**
```bash
# Does deployed need update?
./web4programmer on Web4Programmer 0.1.0.1 needsUpgradeCheck

# Result: ⚠️ UPGRADE RECOMMENDED
# - DefaultWeb4Programmer.ts template 3min newer
```

#### **Phase 6: Discover Methods**
```bash
# What methods does master have?
./web4tscomponent completion method

# What does deployed have?
./web4programmer completion method
# Result: Missing 'tree' command!
```

#### **Phase 7: Verification**
```bash
# Apply fix to master
# (edit DefaultCLI.ts)

# Rebuild
npm run build

# Re-run tests
./web4tscomponent test file 3
# Result: Still 23/23 passing!

# Re-compare
./web4tscomponent compare "Web4TSComponent 0.3.13.1, Web4Programmer 0.1.0.1"
# Result: DefaultCLI.ts now 🟩 Identical
```

### **Learning Extracted**

**Tool Syntax Matters:**
> Small differences in syntax matter! `test 3` vs `test file 3` is the difference between "wrong command" and "running 23 tests". Learn the tools' exact syntax, don't guess.

**Key Insight:** TRON corrected me multiple times on syntax. Each correction was specific: "USE like in the example", "IT IS WRONG USAGE!!!", "learn your tools!!!". The emphasis showed these patterns are important for systematic work.

**Context-Aware Power:**
> The `on Component version command` pattern is incredibly powerful. It lets Web4TSComponent become a universal tool for ALL components, even if they don't have the command themselves. This is radical OOP - the tool adapts to any component.

**Discovery Over Documentation:**
> Don't read docs first - discover! Use `completion method` to see what's available. Use `completion parameter` to see valid values. The tools tell you what they can do. This is self-documenting architecture.

**Hierarchical Test Selection:**
> The test system uses a three-level hierarchy: File (1), Describe (1a), Test (1a1). This allows surgical testing - run one test in 2s instead of all 211 tests in 133s. Perfect for TDD: write test, run that one test, iterate. Use `test itCase` to discover all references instantly.
