## **🎯 PLAN**

### **Context**

**Bug Discovered:** Testing setCICDVersion revealed that `scaffoldComponent()` explicitly sets prod link for ALL versions, overriding setCICDVersion's intelligent build-number-based logic.

**Source:** [2025-10-17-UTC-2025.pdca.md](https://github.com/Cerulean-Circle-GmbH/Web4Articles/blob/dev/2025-10-14-UTC-0948/scrum.pmo/project.journal/2025-10-14-UTC-0948-session/2025-10-17-UTC-2025.pdca.md)

**Current Behavior:**
```
create 0.2.0.4 (build 4)
  ↓ scaffoldComponent() sets prod → 0.2.0.4 (WRONG!)
  ↓ setCICDVersion() sets dev/test → 0.2.0.4 (correct)
Result: prod points to build 4 (should only point to build 0)
```

**Expected Behavior:**
```
create 0.2.0.4 (build 4)
  ↓ setCICDVersion() sets dev/test → 0.2.0.4
  ↓ prod unchanged (stays at build 0)
Result: prod points to build 0, dev/test point to build 4
```

### **Root Cause**

Legacy code in `scaffoldComponent()` method (before setCICDVersion existed) explicitly calls setProd for every created component:

```typescript
// Around line 906-914 in DefaultWeb4TSComponent.ts
console.log(`🔗 Setting prod symlink for ${component}:`);
await this.on(component, version);
await this.setProd();
```

This happens BEFORE `setCICDVersion()` is called, so both methods compete.

### **Solution**

1. Remove explicit `setProd()` call from `scaffoldComponent()`
1. Let `setCICDVersion()` handle ALL semantic links intelligently
1. Build 0 → sets prod
1. Build 1+ → sets dev/test
1. Always sets latest

### **Success Criteria**

1. `scaffoldComponent()` no longer calls `setProd()`
1. `setCICDVersion()` is sole authority for semantic links
1. Test: Create 0.3.0.0 (build 0) → prod set
1. Test: Create 0.3.0.1 (build 1) → dev/test set, prod unchanged
1. All tests pass
