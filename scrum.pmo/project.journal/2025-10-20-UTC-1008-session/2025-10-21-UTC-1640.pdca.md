### Web4 Architectural Principles Discovered

#### 1. **DRY Principle (Don't Repeat Yourself)**

**Definition:**
- Eliminate duplication across code, dependencies, and configuration
- Single source of truth for all shared resources

**Implementation in Web4:**

**A. Dependency Management:**
```bash
# ✅ CORRECT: Symlinked node_modules
project/
├── node_modules/          # Global dependencies (ONE location)
├── Component1/0.1.0.0/
│   └── node_modules -> ../../../node_modules  # Symlink
├── Component2/0.1.0.0/
│   └── node_modules -> ../../../node_modules  # Symlink

# ❌ WRONG: Duplicated node_modules
project/
├── Component1/0.1.0.0/node_modules/  # 100MB
├── Component2/0.1.0.0/node_modules/  # 100MB (duplicated!)
```

**B. Configuration:**
```typescript
// ✅ CORRECT: Extend from root
// components/MyComponent/0.1.0.0/tsconfig.json
{
  "extends": "../../../tsconfig.json"
}

// ❌ WRONG: Duplicate configuration
{
  "compilerOptions": { /* duplicated settings */ }
}
```

**C. Documentation:**
```markdown
✅ CORRECT: Cross-reference
See [How to Component](trainAI how-to-component) for details

❌ WRONG: Copy-paste content
(duplicated explanation here)
```

**D. Code:**
```typescript
// ✅ CORRECT: Reuse existing method
async newMethod(): Promise<this> {
  return this._calculateRelativePathInternal(from, to);
}

// ❌ WRONG: Duplicate logic
async newMethod(): Promise<this> {
  // Copy-pasted calculation logic
}
```

**Why DRY Matters:**
- 💾 Disk space: 100MB → 100MB (not 100MB × N components)
- ⚡ Build time: Install once, not per component
- 🔧 Maintenance: Fix bugs in one place
- ✅ Consistency: Same versions across all components
- 🎯 CMM3 Compliance: Systematic, reproducible, verifiable

#### 2. **Radical OOP (Empty Constructor Pattern)**

**Definition:**
- Constructors are ALWAYS empty (no parameters, minimal initialization)
- All configuration happens via `init(scenario)` method
- Enables zero-dependency instantiation and flexible composition

**Implementation in Web4:**

**A. Empty Constructor:**
```typescript
// ✅ CORRECT: Radical OOP
class MyComponent {
  constructor() {
    this.model = { /* defaults */ };
  }
  
  init(scenario: Scenario<Model>): this {
    // Configuration happens here
    this.model = { ...this.model, ...scenario.model };
    return this;
  }
}

// ❌ WRONG: Constructor with parameters
class MyComponent {
  constructor(config: Config) {  // ❌ NOT radical OOP!
    this.model = config;
  }
}
```

**B. Scenario-Based Initialization:**
```typescript
// Create instance (no knowledge needed!)
const component = new MyComponent();

// Configure via scenario
component.init({
  model: { customSetting: true },
  id: 'scenario-1'
});
```

**Why Radical OOP Matters:**
- 🧪 Testability: `new Component()` always works, no mocking needed
- 🔄 Composition: Chain scenarios for complex configurations
- 🎯 Zero-Knowledge: Anyone can instantiate without docs
- ✅ CMM3: Reproducible initialization patterns
- 🚀 Flexibility: Same component, different scenarios

#### 3. **Method Chaining Pattern**

**Definition:**
- All methods return `Promise<this>`
- Enables fluent API: `component.method1().method2().method3()`

**Implementation:**
```typescript
// ✅ CORRECT: Method chaining
async myMethod(param: string): Promise<this> {
  // Do work
  return this;  // Always return this!
}

// Usage
await component
  .method1('param1')
  .method2('param2')
  .method3();
```

**Why Method Chaining Matters:**
- 📖 Readability: Natural language flow
- 🎯 CLI Integration: `pdca method1 param1 method2 param2`
- 🔄 Context Preservation: State flows through chain
- ✅ CMM3: Systematic operation sequences

#### 4. **Auto-Discovery CLI Pattern**

**Definition:**
- CLI commands are auto-discovered from TypeScript methods
- No manual CLI configuration files
- Annotations drive behavior (`@cliSyntax`, `@cliValues`, `@cliHide`)

**Implementation:**
```typescript
/**
 * Calculate relative path
 * @param fromFile Source file
 * @param toFile Target file
 * @cliSyntax fromFile toFile
 */
async getDualLinkRelativePath(fromFile: string, toFile: string): Promise<this> {
  // Implementation
  return this;
}

// Automatically becomes:
// pdca getDualLinkRelativePath <fromFile> <toFile>
```

**Why Auto-Discovery Matters:**
- 🎯 Zero Configuration: Add method → CLI command appears
- 📖 Self-Documenting: TSDoc becomes CLI help
- ✅ DRY: Single source of truth (TypeScript code)
- 🔧 Maintenance: Change method → CLI updates automatically

#### 5. **Layered Architecture Pattern**

**Definition:**
- layer5: CLI (specific to component)
- layer4: Utilities (reusable helpers)
- layer3: Interfaces (contracts)
- layer2: Implementation (core logic)

**Why Layered Architecture Matters:**
- 🎯 Separation of Concerns: Clear boundaries
- 🔄 Reusability: Lower layers used by higher
- 🧪 Testability: Test layers independently
- ✅ CMM3: Systematic structure

#### 6. **Semantic Versioning with Symlinks**

**Definition:**
- Versions: X.Y.Z.W (major.minor.patch.build)
- Symlinks: `latest` (dev), `prod`, `test`, `dev`
- Automated promotion workflow

**Why Versioning Matters:**
- 🔄 CMM4 Feedback Loop: test → prod → dev
- ✅ Rollback Safety: Prod is always stable
- 🎯 Systematic Evolution: Components evolve without breaking

#### 7. **Positional Parameters (No Flags)**

**Definition:**
- Web4 CLIs use positional parameters ONLY
- No Unix-style `--flags`
- Order defined by `@cliSyntax`

**Example:**
```bash
# ✅ CORRECT: Positional
pdca moveFile <oldPath> <newPath> <?dryRun>

# ❌ WRONG: Flags
pdca moveFile --old <path> --new <path> --dry-run
```

**Why No Flags Matters:**
- 🎯 Simplicity: No complex flag parsing
- ✅ Consistency: All Web4 components identical
- 📖 Readability: Natural language flow
- 🔧 Auto-Discovery: Maps directly to method parameters

### Meta-Learning: Test-First for Documentation

**Discovery:**
- I initially planned to update trainAI WITHOUT writing tests first
- This violates the RAG-Powered Test-First Pattern (how-to-feature-development)
- TRON caught this violation!

**Why test-first for documentation:**
1. ✅ **Objective Verification:** Test proves content exists
2. ✅ **Regression Prevention:** Future changes won't break teaching
3. ✅ **CMM3 Compliance:** Reproducible, verifiable
4. ❌ **Without tests:** Manual checking is subjective, error-prone

**Test structure for trainAI content:**
```typescript
describe('trainAI Web4 Principles', () => {
  it('should teach DRY principle', async () => {
    const output = await captureConsoleOutput(async () => {
      await pdca.trainAI('how-to-component');
    });
    
    expect(output).toContain('DRY: Symlink node_modules');
    expect(output).toContain('never duplicate dependencies');
  });
  
  it('should teach Radical OOP', async () => {
    const output = await captureConsoleOutput(async () => {
      await pdca.trainAI('how-to-component');
    });
    
    expect(output).toContain('Radical OOP: Empty constructors');
    expect(output).toContain('init(scenario)');
  });
});
```

**Pattern: Test-First Even for Documentation**
- Documentation IS code (TypeScript arrays of strings)
- Changes can break teaching
- Tests verify content integrity
- CMM3: Objective, reproducible, verifiable
