### Response (Root Cause Analysis)

#### Original Problem: Links Don't Work in Markdown
```typescript
// getDualLink ORIGINAL SPEC (project-root-relative):
[§/scrum.pmo/.../file.md](scrum.pmo/.../file.md)

```

When this link is placed in `temp/tpichler/linktest.md`:
- Link tries to navigate to: `temp/tpichler/scrum.pmo/.../file.md` ❌
- Should navigate to: `../../scrum.pmo/.../file.md` ✅

#### Design Violation Discovered
**What we did:** Changed `getDualLink` to generate user-location-relative paths
**What we should have done:** Create a NEW method for the new feature!

**Why this is CMM3 Critical:**
1. **Breaking Change:** Existing code depending on `getDualLink` would break
2. **Spec Violation:** Original design doc specified project-root-relative
3. **Method Semantics:** Name doesn't indicate "relative to user location"
4. **Backward Compatibility:** Users expect consistent behavior

#### Correct Solution
Create TWO methods:
1. **`getDualLink`** (ORIGINAL): Project-root-relative paths
2. **`getDualLinkRelative`** (NEW): User-location-relative paths

### Outcome (Solution Design)

#### Final Design (After Correction)

**Method 1: `getDualLink(filePath)` - RESTORED ORIGINAL SPEC**
```typescript
async getDualLink(filePath: string): Promise<this>
// Returns: [GitHub](...) | [§/path](path)  ← project-root-relative
// Use case: Chat reports, documentation, stable references
```

**Method 2: `getDualLinkRelative(filePath, fromDirectory?)` - NEW FEATURE**
```typescript
async getDualLinkRelative(filePath: string, fromDirectory: string = ""): Promise<this>
// Returns: [GitHub](...) | [§/path](../../relative)  ← user-location-relative
// Use case: Markdown files that need clickable links
```

**Comparison:**
| Aspect | getDualLink | getDualLinkRelative |
|--------|-------------|---------------------|
| Path type | Project-root-relative | User-location-relative |
| Example | `(scrum.pmo/.../file.md)` | `(../../scrum.pmo/.../file.md)` |
| Works in | Chat, docs, anywhere | Markdown viewers, VS Code |
| Constant | ✅ Same everywhere | ❌ Changes per location |
| Clickable | ❌ Only at project root | ✅ Anywhere |

## 4. Act

### Learnings

#### Critical Insight: CLI Script State Changes
**Problem:** `process.cwd()` returns where the script runs, NOT where user called it from.

**Root Cause:** The `scripts/pdca` bash script does `cd "$COMPONENT_PATH"` (line 34), changing the working directory to `components/PDCA/latest/`.

**Solution:** Capture `PWD` **BEFORE** any `cd` commands in the bash script:
```bash
export USER_PWD="$PWD"  # Line 9, before any cd
```

Then use it in TypeScript:
```typescript
const userPwd = process.env.USER_PWD || process.env.PWD || process.cwd();
```

#### CLI Optional Parameter Pattern
**Wrong:** `fromDirectory?: string` + `@cliSyntax filePath <?fromDirectory>`
**Right:** `fromDirectory: string = ""` + `@cliSyntax filePath fromDirectory` + `@cliDefault fromDirectory ""`

The CLI auto-discovery requires:
1. Default value in function signature (`= ""`)
2. `@cliDefault` annotation
3. NO `?` in `@cliSyntax`

#### Meta-Learning: Test-Driven Debug
Writing test cases FIRST helped immediately identify:
- What the correct behavior should be
- How to verify it
- Edge cases to consider

#### 🚨 CRITICAL LEARNING: Don't Modify, Extend! 🚨

**The BIG Mistake:**
We CHANGED `getDualLink` behavior instead of creating a NEW method!

**Why This is Dangerous:**
1. **Breaking Changes:** Existing code breaks silently
2. **Spec Violation:** Original design intent lost
3. **User Confusion:** Same method name, different behavior
4. **No Migration Path:** How do users update their code?

**CMM4 Pattern:**
- ❌ **CMM2:** Change existing method behavior
- ✅ **CMM3:** Create new method, deprecate old (if needed)
- ✅ **CMM4:** Evolve by ADDING, not CHANGING

**Correct Approach:**
1. Keep `getDualLink` with original spec (project-root-relative)
2. Add `getDualLinkRelative` for new feature (user-location-relative)
3. Document use cases for each
4. Let users CHOOSE based on their needs

**This violation was caught by user review** - reinforcing the importance of:
- Clear specs
- User testing
- Backward compatibility mindset
