## 📋 PLAN

### Situation
After creating automated test TC39 to reproduce the `moveFile` relative link bug, I manually ran `pdca moveFile` to verify the bug existed, instead of trusting the automated test.

**User question:** "did you need to manually verify that the test did fail?"

### Problem Analysis
**Pattern Violation:** Manual verification when automated test exists.

**Root Causes:**
1. **Test Infrastructure Assumption:** The test had a graceful skip when git wasn't ready, so I assumed it wouldn't show the actual bug
2. **Lack of Trust in Tests:** Didn't trust that the automated test would properly demonstrate the failure
3. **Missing Test Execution Step:** Should have run the test FIRST before any manual verification
4. **CMM3 Violation:** Manual steps when automated verification exists

**What Should Have Happened:**
1. Create automated test TC39 ✅
2. Run test: `web4tscomponent on PDCA latest test itCase 2a1` ✅
3. **OBSERVE test output** (test should FAIL showing the bug) ⚠️
4. Fix the code
5. Run test again (test should PASS)
6. Auto-promote to production

**What Actually Happened:**
1. Create automated test TC39 ✅
2. Manually run `pdca moveFile` to verify bug ❌
3. Manually inspect file contents ❌
4. Then tried to run test (but had path issues)

## 🔄 DO

### Implementation Steps

#### 1. Pattern Definition: Test-First Verification

**CMM3 Rule:** When an automated test exists, ALWAYS run the test FIRST before any manual verification.

**Workflow:**
```
1. Create/Update automated test
2. Run test → Observe output
3. STOP and wait for user direction
4. (If user directs) Fix code
5. Run test again → Observe output
6. Repeat 4-5 until test passes
```

**Anti-Pattern (What I Did):**
```
1. Create automated test
2. Manually verify the bug exists ❌
3. Then try to run test
```

#### 2. Deep Root Cause Analysis

**Why did I manually verify?**

a) **Test Uncertainty:**
   - TC39 had a graceful skip mechanism for git issues
   - I wasn't sure if the test would actually demonstrate the bug
   - **Correct response:** Run the test and SEE what happens

b) **Efficiency Bias:**
   - Thought manual verification would be "faster"
   - **Reality:** Manual verification took longer and violated CMM3

c) **Missing Verification Step:**
   - Created the test but didn't run it immediately
   - **Pattern:** Always run test immediately after creation to verify it works

d) **Low Trust in Test Infrastructure:**
   - Didn't trust that the test would properly show the failure
   - **CMM4 Learning:** Tests are the source of truth - trust them first

#### 3. Comparison to Previous Meta-Learning

**Previous Pattern (2025-10-21-UTC-1007):**
- User said "show me X"
- I did X, analyzed it, fixed it, committed - all without stopping ❌
- **Learning:** STOP after showing X

**Current Pattern (2025-10-21-UTC-1410):**
- User said "create automated test"
- I created test, then manually verified instead of running test ❌
- **Learning:** RUN TEST after creating it

**Common Theme:** Not following the defined process, adding extra subjective steps.

#### 4. CMM4 Principle: Automation Hierarchy

```
1. Automated test exists → Run the test (HIGHEST PRIORITY)
2. No automated test exists → Create test first, then run it
3. Test can't be automated → Document manual steps (LAST RESORT)
```

**Never:** Create automated test AND do manual verification in parallel.

### Lessons Learned

1. **Tests Are Authority:** Automated tests are CMM3-compliant, manual verification is CMM2 (subjective)
2. **Immediate Test Execution:** Always run test immediately after creating it
3. **Trust The Process:** If test output is unclear, improve the test - don't bypass it
4. **Stop After Test:** Show test output and STOP - wait for user direction
5. **Pattern Consistency:** This connects to previous meta-learning about stopping at feedback points
