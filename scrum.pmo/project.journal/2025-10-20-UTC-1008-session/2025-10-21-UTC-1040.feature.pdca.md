## 1. Plan

### Trigger (Verbatim User Request)

**User:** "good. next patch for the component pdca is to add the 'Move' Functionality. Based on what you know, using the DRY and zero knowlede, define it in a pdca.feature.md"

**Context:** After successfully implementing trainAI extensions with zero-knowledge atomic methods, user requests a new feature for moving files with automatic link management.

### Response (Feature Analysis)

#### The Problem

**Current state:**
When a file needs to be moved:
1. User manually moves file: `mv oldpath newpath`
2. User updates links: `pdca updateLinksToFile oldpath newpath`
3. User refreshes relative links: `pdca refreshRelativeLinks newpath`
4. User commits: `git add -A && git commit && git push`

**Issues:**
- 4 manual steps = 4 failure points
- Need to remember exact order
- Cognitive load: Which methods to call?
- Not zero-knowledge: Need to know the process

**What's needed:**
A single, atomic, zero-knowledge method that does everything:
```bash
pdca moveFile oldpath newpath
```

**Result:**
- File moved ✅
- All links updated ✅
- Relative links refreshed ✅
- Changes committed and pushed ✅
- Zero knowledge required ✅

#### DRY Analysis

**Existing methods to reuse:**

1. **File system operations:**
   - `git mv oldPath newPath` - preserves git history (NOT fs.renameSync)

2. **Link management (already implemented):**
   - `updateLinksToFile(oldPath, newPath)` - updates all references
   - `refreshRelativeLinks(filePath)` - recalculates relative links
   - `getDualLink(filePath)` - generates canonical link (for verification)

3. **Git operations:**
   - `git mv` - preserves git history (built-in git command)
   - `git add -A` - stage all changes (built-in git command)
   - `git commit` and `git push` - commit workflow (built-in git commands)

4. **Path normalization (already implemented):**
   - `normalizePath(path)` - ensures consistent path format
   - Used in all existing methods

**DRY principle:**
`moveFile` should orchestrate existing methods and use git-native commands for file operations.

#### Zero-Knowledge Design

**Interface:**
```typescript
async moveFile(oldPath: string, newPath: string, dryRun: string = 'false'): Promise<this>
```

**User experience:**
```bash
# User wants to move a file
pdca moveFile scrum.pmo/old/file.md scrum.pmo/new/location/file.md

# Agent sees:
✅ File moved: scrum.pmo/old/file.md → scrum.pmo/new/location/file.md
✅ Updated 3 markdown files with links to this file
✅ Refreshed relative links in moved file
✅ Changes committed and pushed

# User knows: DONE. No manual steps needed.
```

**What user does NOT need to know:**
- ❌ How to find files linking to moved file
- ❌ How to update dual link format
- ❌ How to recalculate relative paths
- ❌ When to refresh vs when to update
- ❌ Git commit workflow
- ❌ Error handling logic

**Zero-knowledge achieved:** One command, everything handled.

### Outcome (Feature Specification)

#### Method Signature

```typescript
/**
 * Move a file and automatically update all links across the project
 * CMM3 Atomic: Single command handles file move, link updates, relative path refresh, and git operations
 * Zero-knowledge: User only needs to know old path and new path
 * 
 * Process:
 * 1. Validate paths exist/available
 * 2. Move file using fs.renameSync
 * 3. Update all links in other files (updateLinksToFile)
 * 4. Refresh relative links in moved file (refreshRelativeLinks)
 * 5. Git add, commit, push changes
 * 6. Report summary
 * 
 * @param oldPath Current file path (project-root-relative)
 * @param newPath Destination file path (project-root-relative)
 * @param dryRun If 'true', preview actions without executing (default: 'false')
 * @returns this (for method chaining)
 * 
 * @example
 * // Move a PDCA file to new location
 * pdca moveFile "scrum.pmo/old/2025-10-21.pdca.md" "scrum.pmo/new/2025-10-21.pdca.md"
 * 
 * // Preview move without executing
 * pdca moveFile "scrum.pmo/old/file.md" "scrum.pmo/new/file.md" true
 * 
 * @cliSyntax oldPath newPath dryRun
 * @cliDefault dryRun false
 * @cliValues dryRun true false
 */
async moveFile(oldPath: string, newPath: string, dryRun: string = 'false'): Promise<this>
```

#### Algorithm (Detailed)

**Step 1: Input Validation**
```typescript
const isDryRun = dryRun === 'true';
const oldNormalized = this.normalizePath(oldPath);
const newNormalized = this.normalizePath(newPath);

// Check old file exists
if (!fs.existsSync(oldNormalized)) {
  console.error(`❌ Error: Source file not found: ${oldNormalized}`);
  return this;
}

// Check new path directory exists
const newDir = path.dirname(newNormalized);
if (!fs.existsSync(newDir)) {
  console.error(`❌ Error: Destination directory does not exist: ${newDir}`);
  console.log(`💡 Create directory first: mkdir -p ${newDir}`);
  return this;
}

// Check new file doesn't already exist
if (fs.existsSync(newNormalized)) {
  console.error(`❌ Error: Destination file already exists: ${newNormalized}`);
  return this;
}
```

**Step 2: Display Plan**
```typescript
console.log(`\n🔄 Moving File${isDryRun ? ' (DRY RUN)' : ''}\n`);
console.log(`📂 From: ${oldNormalized}`);
console.log(`📂 To:   ${newNormalized}\n`);

if (isDryRun) {
  console.log(`📋 Planned Actions:`);
  console.log(`   1. Move file: ${oldNormalized} → ${newNormalized}`);
  console.log(`   2. Find and update links in other files`);
  console.log(`   3. Refresh relative links in moved file`);
  console.log(`   4. Git commit and push changes\n`);
}
```

**Step 3: Execute Move (Use git mv to preserve history)**
```typescript
if (!isDryRun) {
  console.log(`🚀 Step 1: Moving file (git mv preserves history)...`);
  
  const { execSync } = await import('child_process');
  const projectRoot = this.getProjectRoot();
  
  try {
    execSync(`git mv "${oldNormalized}" "${newNormalized}"`, {
      cwd: projectRoot,
      stdio: 'pipe'
    });
    console.log(`✅ File moved successfully (history preserved)\n`);
  } catch (error: any) {
    console.error(`❌ Error moving file: ${error.message}`);
    return this;
  }
} else {
  console.log(`✓ Would move file using git mv (preserves history)\n`);
}
```

**Why git mv instead of fs.renameSync:**
- ✅ Preserves git history (file shows as renamed, not deleted + created)
- ✅ Maintains blame information (can trace changes across rename)
- ✅ Better for large files (git knows it's the same file)
- ✅ Atomic operation in git (consistent with other git operations)
- ❌ fs.renameSync: Git sees as delete + create (history lost)

**Step 4: Update Links in Other Files (DRY: Reuse updateLinksToFile)**
```typescript
console.log(`🔗 Step 2: Updating links in other files...`);

// DRY: Call existing updateLinksToFile method
// Pass dryRun to preserve dry-run mode
await this.updateLinksToFile(oldPath, newPath, dryRun);

// updateLinksToFile already handles:
// - Finding all markdown files
// - Detecting dual links
// - Updating both GitHub and local paths
// - Preserving relative/absolute nature
// - Reporting results
// - Auto-committing (if not dry-run)

console.log(); // Spacing
```

**Step 5: Refresh Relative Links (DRY: Reuse refreshRelativeLinks)**
```typescript
console.log(`🔄 Step 3: Refreshing relative links in moved file...`);

// DRY: Call existing refreshRelativeLinks method
// This recalculates all relative paths based on new location
await this.refreshRelativeLinks(newPath, dryRun);

// refreshRelativeLinks already handles:
// - Scanning moved file for dual links
// - Detecting relative paths
// - Recalculating from new location
// - Updating file content
// - Reporting results

console.log(); // Spacing
```

**Step 6: Git Operations (Commit and push - file already staged by git mv)**
```typescript
if (!isDryRun) {
  console.log(`📦 Step 4: Committing changes...`);
  
  // Note: git mv already staged the file move
  // We only need to commit additional changes (link updates, relative refreshes)
  
  const commitMessage = `refactor: move ${path.basename(oldNormalized)} to new location

Moved: ${oldNormalized} → ${newNormalized}
Updated: All references to this file
Refreshed: Relative links within file

Auto-committed by pdca moveFile`;

  const { execSync } = await import('child_process');
  const projectRoot = this.getProjectRoot();
  
  try {
    // Add any modified files (link updates)
    execSync(`git add -A`, { cwd: projectRoot, stdio: 'pipe' });
    
    // Commit (includes the git mv + link updates)
    execSync(`git commit -m "${commitMessage}"`, {
      cwd: projectRoot,
      stdio: 'pipe'
    });
    
    // Push
    execSync(`git push`, {
      cwd: projectRoot,
      stdio: 'pipe'
    });
    
    console.log(`✅ Changes committed and pushed\n`);
  } catch (error: any) {
    console.error(`❌ Git operation failed: ${error.message}`);
    return this;
  }
} else {
  console.log(`✓ Would commit and push changes\n`);
}
```

**Note on git workflow:**
- `git mv` automatically stages the rename
- Additional `git add -A` captures link updates in other files
- Single commit contains: rename + link updates + relative refreshes
- Preserves atomicity: all changes are one logical unit

**Step 7: Summary Report**
```typescript
console.log(`📊 Summary:`);
console.log(`   - File moved: ${oldNormalized} → ${newNormalized}`);
console.log(`   - Links updated in other files: See updateLinksToFile output above`);
console.log(`   - Relative links refreshed in moved file: See refreshRelativeLinks output above`);

if (isDryRun) {
  console.log(`\n💡 Run without 'true' to execute: pdca moveFile "${oldPath}" "${newPath}"`);
} else {
  console.log(`\n✨ Move complete! All links are valid and up-to-date.`);
}

return this;
```

## 4. Act

### Learnings

#### Git History Preservation

**Critical correction:**
Initial design used `fs.renameSync()` which is a file system operation.

**Problem:**
- fs.rename → Git sees as delete + create
- History lost: `git blame` shows new file
- Large files: Git stores duplicate content
- CMM2 violation: Not using proper git tools

**Correct approach:**
Use `git mv` instead:
- ✅ Git sees as rename (history preserved)
- ✅ `git blame` works across rename
- ✅ `git log --follow` traces file history
- ✅ Git stores efficiently (knows it's same content)
- ✅ CMM3: Uses proper git workflow

**Command:**
```bash
git mv oldPath newPath
```

**Integration:**
- `git mv` stages the rename automatically
- Additional changes (link updates) staged with `git add -A`
- Single commit contains all changes
- Atomic operation maintained

**Learning:**
Always use git-native commands for file operations in version-controlled projects.
File system operations bypass git tracking = lost history.

#### The CMM3 Atomic Method Pattern

**What we're seeing:**
Every new method follows this pattern:

1. **Single entry point** (e.g., `moveFile`)
2. **Orchestrates existing methods** (DRY)
3. **Handles all edge cases** (error messages)
4. **Zero knowledge interface** (simple inputs)
5. **Comprehensive reporting** (user sees progress)

**This is becoming a reusable pattern:**
```
New atomic method = Validate + Orchestrate + Report + Error handle
```

**Next methods can follow this template:**

- `deleteFile` - with link cleanup and git commit
- `renameComponent` - move entire component directory

#### DRY at Method Level

**Discovery:**
We're not just avoiding code duplication—we're avoiding **process duplication**.

**Before moveFile:**
```
Agent thinks:
"How do I move a file?"
→ Remember file move command
→ Remember link update method
→ Remember relative refresh method
→ Remember git workflow
→ Execute 4 commands
```

**After moveFile:**
```
Agent thinks:
"How do I move a file?"
→ Call moveFile
→ Done
```

**The DRY principle applied to cognitive processes:**
Don't make agents repeat the same thought process.
Encapsulate common workflows into atomic methods.
