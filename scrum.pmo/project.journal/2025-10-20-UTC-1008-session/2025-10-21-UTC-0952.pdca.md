### Trigger (Verbatim User Report)

**Context:** Test failure - TC22.5 looking for `test123.feature.pdca.md` which no longer exists.

**Agent's Initial Response:** "Use an existing stable file like `package.json` or `README.md`"

**User's Response:** "you are wrong choosing Option 1. how can you create a resilient system that you are aware of its state ALWAYS? in the option 1 case you are just assuming based on probability that the readme will always be there but you do not know and also cannot use a file that is there for a reason to test with it!"

**Critical Insight:** Tests must **create and control** their own state, not **assume** external state exists.

### Response (Root Cause Analysis)

#### The Violation: CMM2 "Probability-Based" Testing

**What I did wrong:**
```typescript
// ❌ CMM2: Assume file exists
pdca.getDualLink('README.md')  // "It's probably there"
```

**Why this is CMM2:**
1. **Assumption-based:** "File probably exists"
2. **Not reproducible:** File might be renamed/deleted
3. **Not verifiable:** Can't verify assumption before test
4. **External dependency:** Test depends on state outside its control
5. **Fragile:** Breaks when external state changes

#### The Correct Approach: CMM3 State Management

**CMM3 Principle:** Tests must **guarantee** their required state exists.

```typescript
// ✅ CMM3: Ensure state exists
beforeAll(async () => {
  // 1. CREATE test state (don't assume)
  const testFile = 'test/data/dual-link-tests/tc22-5-target.md';
  
  // 2. ENSURE file exists
  if (!existsSync(testFile)) {
    await writeFile(testFile, '# Test fixture for TC22.5');
  }
  
  // 3. ENSURE git state is ready
  ensureGitReady(testFile);  // add, commit, push if needed
  
  // 4. NOW we KNOW the state!
});
```

### Outcome (Solution Design)

#### Test Fixture Management Strategy

**Pattern 1: Dynamic Fixtures (beforeAll/afterAll)**
```typescript
beforeAll(async () => {
  // Create test fixtures
  await createTestFile('test/data/fixture.md');
  await ensureGitReady('test/data/fixture.md');
});

afterAll(async () => {
  // Optional: cleanup or keep for inspection
});
```

**Pattern 2: Stable Fixtures (test/data/ with verification)**
```typescript
const FIXTURES = {
  TC22_5: 'test/data/dual-link-tests/tc22-5-target.md'
};

beforeAll(async () => {
  // Verify fixture exists, create if missing
  for (const [name, path] of Object.entries(FIXTURES)) {
    if (!existsSync(path)) {
      throw new Error(`Test fixture missing: ${name} at ${path}`);
      // OR: await createFixture(path);
    }
    await ensureGitReady(path);
  }
});
```

**Chosen: Pattern 2** - Stable fixtures with verification
- Test data lives in `test/data/`
- Version-controlled and documented
- Verified before each test run
- Can be recreated if missing

```typescript
async function ensureGitReady(filePath: string) {
  // Check if file is added
  const status = execSync(`git status --porcelain "${filePath}"`);
  if (status.includes('??')) {
    execSync(`git add "${filePath}"`);
  }
  
  // Check if committed
  try {
    execSync(`git log --oneline -1 -- "${filePath}"`);
  } catch {
    execSync(`git commit -m "test: add fixture ${filePath}"`);
  }
  
  // Check if pushed (optional for local tests)
  // Can be skipped for CI/local environments
}
```

## 4. Act

### Learnings

#### 🚨 CMM3 Critical Principle: No Assumptions in Tests 🚨

**The Mistake:**
"Use existing files like README.md or package.json for tests"

**Why It's Wrong:**
1. **Probabilistic:** Assumes files exist (they probably do... but not guaranteed)
2. **External dependency:** Test doesn't control the state
3. **Fragile:** Breaks when files are renamed/deleted
4. **Not reproducible:** Can't guarantee same state across runs
5. **Wrong purpose:** Using production files for test purposes

**The Correct Approach:**
"Tests must **create, verify, and control** their own state"

**CMM Levels:**
- ❌ **CMM1:** No tests
- ❌ **CMM2:** Tests that assume state ("it works on my machine")
- ✅ **CMM3:** Tests that guarantee state (reproducible, verifiable)
- ✅ **CMM4:** Tests that evolve with the system (feedback loop)

#### Meta-Pattern: Question Assumptions

**When I said "use package.json":**
- I was **assuming** it exists
- I was **hoping** it won't change
- I was being **lazy** (easier than creating fixtures)

**When user challenged me:**
- Forced me to think about **guarantees** vs **probabilities**
- Reminded me of **CMM3 principles** (objective, reproducible)
- Taught me to **control state** instead of assuming it

**This applies everywhere:**
- File operations: Don't assume paths exist
- Git operations: Don't assume branch/commit exists
- Dependencies: Don't assume packages installed
- Configuration: Don't assume settings present
