## 📚 TrainAI Integration Plan

### New Topic Required: `how-to-test-without-versioning`

**Why This Topic:**
- Agents need to know how to verify baseline without triggering version creation
- The `web4tscomponent test itCase` functionality is a **zero-knowledge tool**
- Without this knowledge, agents will use `pdca test` and create unwanted versions
- This is a CMM3 gap: The capability exists but isn't documented in RAG

**Proposed Content:**

**Topic Name:** `how-to-test-without-versioning`  
**Title:** 🧪 How to Test Without Versioning: Baseline Verification

**Required Reading:**
- `components/Web4TSComponent/README.md` (test itCase functionality)
- `scrum.pmo/how.to/howto.test-workflow.md` (versioning lifecycle)

**Key Lessons:**

1. **Viewing Tests:**
   - `web4tscomponent on <Component> latest test itCase` shows complete test tree
   - Displays: file number, describe blocks, test cases with tokens
   - No execution, no versioning

2. **Running Specific Tests:**
   - `web4tscomponent on <Component> latest test itCase <token>` (e.g., 5a1)
   - Runs ONLY that test using vitest filtering
   - Safe for baseline checks

3. **Running All Tests:**
   - `cd components/<Component>/latest && npx vitest run`
   - Direct vitest call bypasses auto-promotion
   - Useful for comprehensive baseline verification

4. **When to Use:**
   - ✅ Before refactoring (establish baseline)
   - ✅ During debugging (isolate failures)
   - ✅ When testing in `latest` (not ready for auto-promotion)
   - ❌ When ready to promote (use `pdca test` instead)

5. **Why NOT `pdca test`:**
   - `pdca test` triggers auto-promotion workflow
   - Creates new `test` version on success
   - Creates new `prod` and `dev` versions
   - Not suitable for baseline checks

6. **Test Tokens:**
   - Format: `<file><describe><test>` (e.g., 5a1, 3b2)
   - File: Test file number (1-7)
   - Describe: Describe block letter (a, b, c)
   - Test: Test case number (1, 2, 3)

7. **Zero-Knowledge Principle:**
   - Use `web4tscomponent test itCase` FIRST to discover tests
   - Don't assume test names or structure
   - Let the tool show you what exists

**Verification Checklist:**
- [ ] Can view test tree without executing tests
- [ ] Can run specific test by token
- [ ] Understands when to use `itCase` vs `pdca test`
- [ ] Knows how to establish baseline before refactoring
- [ ] Recognizes `pdca test` creates versions
- [ ] Can explain test token format
- [ ] Uses zero-knowledge approach (discover, don't assume)

**Example Workflow:**
```bash

# 5. When ready: promote

```
