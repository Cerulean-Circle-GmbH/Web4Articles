## PLAN

### Problem Statement

**User's Challenge:**
> "this project is open source and many users can work with an agent that is in different 'state of mind'. they are all producing valuable insights. we need to create a process that collects it, consolidates and then update the RAG system which is the short term memory of every agent."

> "we cannot let everybody change it without having it in a defined way. so we need to define it and to think about the ability for conflict free merging across all developers."

### Core Problem Analysis

**Multi-Agent Knowledge Evolution:**
- Multiple developers → Multiple agents → Multiple "states of mind"
- Each agent produces valuable insights (meta-learnings from PDCAs)
- These insights need to be collected, consolidated, and integrated into trainAI (RAG system)
- trainAI is the "short memory" for ALL agents across ALL developers

**The Conflict:**
- Developer A's agent learns Pattern X → Updates trainAI
- Developer B's agent learns Pattern Y → Updates trainAI
- Both patterns valid, but merge conflict inevitable if not structured correctly
- **Cannot allow uncontrolled updates** - need CMM3 defined process

**The Challenge:**
1. **Collection:** How to gather insights from multiple agents?
2. **Consolidation:** How to merge knowledge without conflicts?
3. **Validation:** How to ensure quality before RAG integration?
4. **Distribution:** How to update all agents' memory?
5. **Versioning:** How to track trainAI evolution?
6. **Conflict-Free Merge:** How to enable parallel contributions?

### Existing Web4 Patterns (from RAG Query)

**Component Upgrade Workflow:**
- Semantic versioning: `latest`, `test`, `dev`, `prod`
- Auto-promotion workflow: Work on latest → Test → Promote
- NEVER manual symlink manipulation

**Merge Workflow:**
- Post-merge checklist: Resolve → Commit → Build → Test → Verify
- Source merge ≠ Complete integration
- Symlinks auto-accepted, may point to unbuilt versions

**Feature Development:**
- Phase 0: RAG preparation (query BEFORE planning)
- Phase 6: trainAI integration (close knowledge loop immediately)

### Proposed Solution Architecture

**Inspired by Git Pull Request Model:**

```
Developer Branch (feature/agent-learns-X)
    ↓
    Creates: trainai-update-proposal.json (structured data)
    ↓
    Pull Request → Main TrainAI Branch
    ↓
    Validation: Schema check, conflict detection, quality gate
    ↓
    Consolidation: Merge proposals (structured, conflict-free)
    ↓
    Integration: Update trainAI markdown files
    ↓
    Promotion: latest → test → prod (semantic versioning)
    ↓
    Distribution: All agents pull updated trainAI
```

### Key Design Decisions

**1. Structured Data Format (JSON) for Proposals**
- Not direct markdown edits (causes merge conflicts)
- Structured proposals that can be merged programmatically
- Schema-validated to ensure quality

**2. Semantic Versioning for TrainAI Itself**
- trainAI has versions: 1.0.0, 1.1.0, 1.2.0
- Breaking changes → Major version
- New topics → Minor version
- Topic updates → Patch version

**3. Proposal-Based Workflow (Not Direct Edits)**
- Agent creates proposal: `pdca trainAI updateTrainAI <proposal-file>`
- Proposal reviewed, validated, consolidated
- Integrated by maintainer or automated system

**4. Conflict-Free Merge via Structured Data**
- JSON proposals can be merged without text conflicts
- Each proposal is atomic (self-contained)
- Proposals reference topics/sections, don't modify them directly

### Detailed Feature Specification

#### Method 1: `trainAI updateTrainAI <proposal-file>`

**Purpose:** Submit a structured proposal to update trainAI

**Parameters:**
- `proposal-file`: Path to JSON proposal file (e.g., `trainai-update-proposal.json`)

**Workflow:**
1. Validate proposal schema
2. Check for duplicates (already proposed?)
3. Create proposal branch (e.g., `trainai-update/2025-10-27-UTC-1535`)
4. Commit proposal to `proposals/` directory
5. Output instructions for pull request

**Proposal Schema:**
```typescript
interface TrainAIUpdateProposal {
  version: string;              // Proposal schema version (1.0.0)
  proposedBy: {
    agent: string;              // "Claude Sonnet 4.5" | "GPT-4" | etc
    developer: string;          // GitHub username or "anonymous"
    session: string;            // Session ID (e.g., "2025-10-20-UTC-1008-session")
    pdca: string;               // Source PDCA file path
  };
  proposalType: "new-topic" | "update-topic" | "new-section" | "update-section" | "new-pattern" | "fix-error";
  targetTopic: string;          // Topic number (e.g., "1" for start) or "21" for new
  targetSection?: string;       // Section name (e.g., "Recovery After Extended Break")
  priority: "critical" | "high" | "medium" | "low";
  title: string;                // Short description (e.g., "Add Pretrained State section")
  description: string;          // Detailed explanation of WHY this update is needed
  sourceEvidence: string[];     // PDCAs or files that demonstrate need
  proposedContent: {
    insertionPoint?: string;    // Where to add (e.g., "Section 0", "Line 180", "After X")
    contentType: "markdown" | "checklist" | "example" | "reference";
    content: string;            // The actual content to add/update
  };
  impactAnalysis: {
    affectsTopics: string[];    // Other topics that reference this
    breakingChange: boolean;    // Does this change existing behavior?
    estimatedLines: number;     // Content length
  };
  validation: {
    testedBy?: string;          // How was this tested? (e.g., "Applied to Topic 1, agent read and followed")
    verifiedBy?: string[];      // Other developers/agents who verified
  };
  relatedProposals?: string[];  // IDs of related proposals
}
```

### Conflict-Free Merge Strategy

**Problem:** Multiple developers propose updates to same topic/section

**Solution: Proposal Queue + Consolidation**

**Scenario:**
- Developer A proposes: Topic 1, add Section 0 (Pretrained State)
- Developer B proposes: Topic 1, add Section 2 (Recovery Protocol)

**Strategy:**
1. Both proposals accepted (no conflict - different sections)
2. Integration order determined by:
   - Priority (critical > high > medium > low)
   - Insertion point (Section 0 before Section 2)
   - Dependency (B depends on A? Integrate A first)

**Scenario: Actual Conflict**
- Developer A proposes: Topic 1, Section 0 (version A content)
- Developer B proposes: Topic 1, Section 0 (version B content)

**Strategy:**
1. Detect conflict (same target, same section)
2. Create conflict resolution proposal:
   ```json
   {
     "proposalType": "conflict-resolution",
     "conflictingProposals": ["2025-10-27-001", "2025-10-27-015"],
     "resolutionStrategy": "merge-both" | "choose-A" | "choose-B" | "create-new",
     "mergedContent": "..."
   }
   ```
3. Maintainer reviews and resolves
4. Original proposals marked as "resolved-by-X"

**Test 8: Version Increment Logic**
```typescript
it('should increment version based on change type', async () => {

  expect(patchResult.versionAfter).toBe('1.0.1'); // 1.0.0 → 1.0.1

  const major = createProposal({ type: 'update-section', breaking: true });
```
