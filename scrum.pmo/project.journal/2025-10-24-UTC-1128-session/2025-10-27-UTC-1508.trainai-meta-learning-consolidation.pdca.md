#### 4. Post-Break Recovery Protocol (2025-10-27-UTC-0918)

**CRITICAL Pattern: Baseline Test ALL**
- **User Correction:** "You need to test ALL executables in baseline AND verify"
- **Agent's Mistake:** Planned to test only one item
- **Fix:** Test ALL (web4tscomponent, pdca, licensetool) in Step 1, again in Step 5
- **Lesson:** Establish complete BEFORE state, complete AFTER state, compare

**Pattern: DRY in PDCA**
- **Anti-Pattern:** Duplicating step lists in Expected Output vs DO section
- **Result:** Inconsistency, confusion, errors
- **Fix:** Define test-first pattern ONCE in Expected Output, reference (don't duplicate) in DO
- **Lesson:** Single source of truth for execution steps

**Pattern: CHECK Section Format**
- **Wrong:** Write expected/predicted results
- **Right:** Write placeholders for ACTUAL results (objective evidence)
- Example: `[ ] web4tscomponent output: [Document ACTUAL error or success]`
- **Lesson:** CHECK documents evidence, not predictions

**Pattern: Self-Consistency Verification**
- **Failure:** Agent learned "Web4 uses positional params" but wrote `web4tscomponent --help` in plan
- **Root Cause:** Knowledge acquisition disconnected from knowledge application
- **Fix:** Re-read own written content, verify against learned patterns
- **Lesson:** Learned knowledge is useless if not applied consistently

**Pattern: Reading Depth 3 Protocol**
- Document → References → Secondary references
- Not automatic, must be explicitly followed
- **Lesson:** Reading breadcrumbs prevents assumption cascade

#### 5. Temporal Debugging (2025-10-27-UTC-1208, 2025-10-27-UTC-1249)

**Pattern: Required vs Optional Parameters**
- **Bug:** Method with required parameter called without args
- **Symptom:** CLI routing falls through to wrong method
- **Fix:** Add default parameter value
- **Lesson:** All user-facing CLI methods need sensible defaults

**Pattern: Evidence vs Current State**
- User showed evidence from BEFORE fix
- Agent tested AFTER fix
- Result: Appeared to be no bug when there WAS one
- **Lesson:** Verify current state first, then trace history if needed

**Pattern: Test Current State Before History**
- Don't assume bug exists just because user reported it
- Test current behavior first
- Then investigate history to understand what changed
- **Lesson:** Prevent fixing already-fixed bugs

**Current Coverage:** NOT in any topic

#### 6. Migration Testing Pattern (2025-10-27-UTC-1130)

**Pattern: Before/After Migration Testing**
- Must test BEFORE migration (source version)
- Must test AFTER migration (target version)
- Verify parameter signatures match
- Check default values are correct
- **Lesson:** Signature-compatible ≠ behavior-compatible

**Pattern: Version Confusion in Multi-Symlink Architecture**
- `prod`, `test`, `dev`, `latest` can point to different versions
- Always check `component links` before migration
- Verify which version has desired behavior vs bug
- **Lesson:** Don't assume, verify semantic version mappings

## Baseline TEST ALL First Pattern

### The Anti-Pattern
❌ Test only one item → Apply fix → Test only one item
- Missing: What else broke?
- Missing: What stayed working?
- Result: Incomplete understanding of impact

### The Correct Pattern
✅ Test ALL potentially affected items → Apply fix → Test ALL same items
- BEFORE state: Document actual behavior of ALL items
- AFTER state: Document actual behavior of ALL items
- Compare: Objective evidence of what changed

### Example (File Header Recovery)
**Wrong:**
1. Test web4tscomponent → broken
2. Fix headers
3. Test web4tscomponent → working
4. **Missing:** pdca, licensetool may also be broken!

**Right:**
1. Test web4tscomponent, pdca, licensetool → Document ACTUAL status
2. Fix headers
3. Test web4tscomponent, pdca, licensetool → Document ACTUAL status
4. Compare: Which changed? Which stayed same?

### Emergency Situations
⚠️ "Urgent" does NOT override CMM3 baseline testing
- Emergency fix still needs: Baseline ALL → Fix → Verify ALL
- Skipping baseline = Incomplete recovery
- Forcing function: Test-first applies ALWAYS

## DRY Principle & Self-Consistency

### DRY: Don't Repeat Yourself
**Anti-Pattern:** Duplicate step lists in multiple sections
- Expected Output lists: "Step 1, Step 2, Step 3..."
- DO section lists: "Step 1, Step 2, Step 3..." (different details!)
- Result: Inconsistency, confusion, errors

- Expected Output: Define pattern ONCE with key characteristics
- DO section: Reference pattern, add specific commands
- CHECK section: Reference same pattern, add actual results

**Example:**
```
Expected Output:
  Test-First Pattern:
  1. Baseline → 2. Fix → 3. Verify

DO Section:
  Step 1: Baseline (per Test-First Pattern)
    Commands: [specific commands]
  Step 2: Fix (per Test-First Pattern)
    Commands: [specific commands]
  Step 3: Verify (per Test-First Pattern)
    Commands: [specific commands]
```

### CHECK Section Format
**Wrong:** Predictions
- [ ] web4tscomponent will work
- [ ] Shebang will be on line 1
- [ ] Tests will pass

**Right:** Placeholders for actual results
- [ ] web4tscomponent output: [Document ACTUAL - error or success]
- [ ] Shebang position: [Document ACTUAL line number]
- [ ] Test results: [Document ACTUAL output]

## Feature Migration Testing

### The Challenge
Migrating a feature/method from one version to another requires:
- Source version has feature → Target version needs it
- But: Signature compatible ≠ behavior compatible

### Before/After Migration Testing Pattern
1. **Before Migration:**
   - Test source version: `component-vX.Y.Z methodName args`
   - Document ACTUAL behavior (output, side effects)
   - Verify it's the desired behavior to copy

2. **During Migration:**
   - Copy method code
   - Verify parameter signatures match
   - Check default values are correct
   - Verify all helper methods exist in target

3. **After Migration:**
   - Test target version: `component-vA.B.C methodName args`
   - Document ACTUAL behavior
   - Compare to source version (should be identical)

### Version Confusion Prevention
**Multi-Symlink Architecture:**
- `prod` → 0.3.5.0
- `test` → 0.3.5.1
- `dev` → 0.3.5.1
- `latest` → 0.3.4.4

**Before Migration:**
1. Run `component links` to see current mappings
2. Identify which version has desired behavior
3. Identify which version needs the feature
4. Don't assume "latest" = "best" (might be older!)

### Verification Checklist

[ ] Migrated code with all dependencies
[ ] Verified parameter signatures match
